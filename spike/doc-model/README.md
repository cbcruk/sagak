# 1단계 — 위치 매핑

목적은 하나입니다.

> **불변 문서를 택하는 순간 위치 매핑이 의무가 된다는 것을 손으로 겪기.**

`reference-codemirror-state.md` 가 _"불변이라는 선택이 매핑·구조적 공유라는
다음 선택을 강제한다"_ 고 적어 둔 문장을 코드로 확인합니다.

## 성공 기준

"에디터가 돌아감" 이 **아닙니다.** 목표는 특정 실패를 겪는 것입니다 —
`test/why-mapping.test.ts` 가 그것입니다.

```
편집 두 번을 적용할 때, 원래 좌표를 그대로 쓰면 엉뚱한 자리에 들어간다.

  "hello world"  →  "hello" 를 "hi" 로  →  위치 7 에 "big " 삽입
  매핑 없이:  <p>hi worbig ld</p>    ← 틀림
  매핑하고:  <p>hi big world</p>     ← 맞음
```

## 좌표계

ProseMirror 와 같습니다. 위치는 글자가 아니라 **글자 사이의 틈**이고,
**문단의 여닫는 지점도 위치를 하나씩 먹습니다.**

```
doc = [P("ab"), P("cd")]

0     1  2  3     4     5  6  7     8
<p>   a  b  </p>  <p>   c  d  </p>
```

경계가 위치를 먹는 게 처음엔 낭비 같지만, 없으면 "문단 사이" 를 가리킬
방법이 사라집니다. 문단을 새로 넣거나 두 문단을 합치는 편집이 전부 그 자리를
지목해야 합니다.

## `assoc`

위치가 삽입 지점에 **정확히 걸쳤을 때** 앞뒤 어디에 붙을지. 인자 하나지만
나중에 넣으려면 호출부를 전부 다시 봐야 해서 처음부터 넣었습니다.

|      |                                                       |
| ---- | ----------------------------------------------------- |
| `1`  | 삽입된 글자 **뒤** — 타이핑하는 커서                  |
| `-1` | 삽입된 글자 **앞** — 앞에 고정된 표식, 마크 시작 경계 |

빼놓으면 매핑이 "돌아가는데" 커서가 이상하게 굽니다. `test/assoc.test.ts`.

## 검증 — 독립 오라클

`mapPos` 는 자료구조 위의 산술이라 예시 테스트로는 부족합니다. 그래서
문단 텍스트를 **문자 배열이 아니라 id 배열**로 두고 변경을 적용한 뒤,
"원래 `t` 번째 글자가 지금 어디 있나" 를 `indexOf` 로 직접 구합니다.
`mapPos` 와 완전히 독립된 답이라 서로 검산이 됩니다.

씨앗 200개로 돌리고, 실패하면 씨앗이 출력되어 재현됩니다.
(`fast-check` 를 쓰면 반례 축소까지 되지만 의존성을 늘리지 않았습니다.)

**세 가지 고장을 심어 실제로 잡히는 것을 확인했습니다** — `assoc` 무시(1개
실패), 삭제 길이 누락(4개), 접힘 지점 한 칸 밀림(2개).

# 2단계 — `contenteditable` 과 화해하기

`contenteditable` 을 안 쓰겠다는 게 아닙니다. ProseMirror 도 CodeMirror 도
씁니다 — IME 조합, 네이티브 캐럿, 모바일 키보드, 스크린 리더를 포기할 수
없기 때문입니다.

차이는 **누가 진실이냐** 입니다.

|          | 진실 | `contenteditable` 의 역할 |
| -------- | ---- | ------------------------- |
| sagak    | DOM  | 편집 그 자체              |
| PM · CM6 | 모델 | 입력 수단 + 렌더 대상     |

그래서 화살표를 뒤집습니다.

```
beforeinput   막지 않습니다. 커서 위치만 적어 둡니다
     ↓        브라우저가 DOM 을 고칩니다
input         DOM 을 읽어 변경 목록을 만듭니다   (read-dom.ts)
     ↓        모델에 적용합니다                  (change.ts)
     ↓        모델로 DOM 을 다시 그립니다        (view.ts)  ← 네이티브 선택이 죽습니다
     ↓        mapPos 로 커서를 되살립니다        (map.ts)
```

## 성공 기준

1단계 README 가 못박아 둔 종료 조건의 뒷부분입니다.

> 브라우저에서 **한 문단 쓰는 동안 커서가 살아남으면** 멈추고 문서로 정리한다.

`test/reconcile.browser.test.ts` 가 그것입니다.

## 재고 나서 바뀐 것 — IME

1단계 README 에 이렇게 적어 뒀습니다.

> 조합 중인 입력은 `preventDefault` 로 막을 수 없어서…

**결론은 맞았고 이유는 틀렸습니다.** 그건 잰 게 아니라 아는 척한 것이라
2단계의 첫 일로 실제로 쟀습니다 (`test/composition.browser.test.ts`).
CDP `Input.imeSetComposition` 으로 렌더러의 진짜 조합 상태를 만들어
ㅎ→하→한 을 칩니다. 합성 `CompositionEvent` 를 dispatch 하는 건 내 코드가
내 코드를 확인하는 것이라 의미가 없습니다.

크롬이 실제로 하는 말:

| 이벤트                                | `cancelable` | 막으면?      |
| ------------------------------------- | ------------ | ------------ |
| `beforeinput` `insertText`            | `true`       | **막힙니다** |
| `compositionstart`                    | `true`       | 안 막힙니다  |
| `compositionupdate`                   | `true`       | 안 막힙니다  |
| `compositionend`                      | `true`       | 안 막힙니다  |
| `beforeinput` `insertCompositionText` | `false`      | 안 막힙니다  |

조합 이벤트 셋이 전부 취소 가능하다고 **거짓말합니다.** 표준은
`compositionupdate`/`end` 를 취소 불가로 정의하는데도 그렇습니다.
`cancelable` 을 보고 설계하면 틀린다는 뜻이고, 정직한 신호는
`beforeinput` 의 `insertCompositionText` 하나뿐입니다.

전부 `preventDefault` 해도 `한` 은 들어갑니다. 그래서 남는 길은 하나 —
**놔두고, 읽고, 화해시키기.**

부수적으로 나온 사실 하나: `compositionend` 는 **마지막 `input` 뒤에**
옵니다. "조합이 끝나면 `input` 이 한 번 더 오겠지" 하고 기다리는 설계는
그대로 멈춥니다. `EditorView` 가 `compositionend` 에서 직접 flush 하는
이유입니다.

## 매핑이 장식이 아니라는 증거

`renderDoc` 은 문단을 통째로 새로 만듭니다 (ProseMirror 의 DOM 비교
최적화를 일부러 뺐습니다). 그러면 글자 하나 칠 때마다 캐럿이 붙어 있던
텍스트 노드가 사라집니다.

대조군으로 커서 복원을 끄고 `hello` 를 쳐 봤습니다.

```
<p>olleh</p>
```

**글자가 뒤집힙니다.** 다시 그릴 때마다 캐럿이 문단 맨 앞으로 돌아가서
다음 글자가 앞에 붙기 때문입니다. 매핑이 없으면 에디터가 "조금 이상해지는"
게 아니라 아예 못 씁니다.

반대로 매핑이 제대로 붙으면 `mapPos` 의 예측이 **브라우저가 실제로 옮긴
커서와 일치합니다.** 1단계의 id 배열 오라클과 같은 역할을 브라우저가
해 줍니다.

(`writeCaret` 이 항상 위치 1 을 반환하도록 고장 내 보면 10개 중 6개가
실패합니다. 통과가 우연이 아닌지 확인한 것입니다.)

## 알려진 한계 — 진단의 애매함

`read-dom.ts` 는 문자열 둘의 앞뒤 공통 부분을 깎아 차이를 구합니다.
같은 글자가 이어지면 **어디에 쳤는지 문자열만 봐서는 알 수 없습니다.**

`"aaa"` 의 맨 앞에 `a` 를 쳐도 맨 뒤에 넣은 것으로 진단합니다. 텍스트는
어느 쪽으로 봐도 맞으므로 **모델은 멀쩡하고 커서 예측만 어긋납니다.**
그래서 조용합니다 — 브라우저가 보고한 자리라는 정답지가 없었다면 못 찾았을
종류의 버그입니다.

ProseMirror 가 진단에 선택 위치를 섞는 이유가 이것입니다. 2단계에서는
재 두기만 했고, **3단계에서 고쳤습니다.**

# 3단계 — 구조 변경

Enter, Backspace 병합, 문단을 가로지르는 삭제, 여러 문단 붙여넣기.

## 울타리를 친 것은 좌표계가 아니라 변경의 표현이었습니다

1·2단계는 "한 문단 안" 이라는 울타리 안에 있었습니다. 그런데 좌표계는
처음부터 **문단 경계도 위치로 세고 있었습니다** — `paraSize = 텍스트 길이 + 2`.
가리킬 수는 있는데 만들 수가 없었던 것뿐입니다. `insert` 가 글자열이었으니까요.

그래서 `insert` 를 경계를 품을 수 있는 **조각열**로 바꿉니다.

```
texts: ['abc']      →  글자만. 1·2단계와 같습니다
texts: ['a', 'b']   →  a 뒤에서 문단이 갈립니다 (Enter, +2)
texts: ['']         →  범위만 지웁니다. 경계를 지우면 병합 (-2)
```

첫 조각은 왼쪽 문단에, 마지막 조각은 오른쪽 문단에 **녹아듭니다.**
ProseMirror 의 `Slice` 가 `openStart`/`openEnd` 를 들고 다니는 이유가
이것이고, 여기서는 양끝이 열린 경우만 다룹니다.

## `mapPos` 는 한 줄도 안 바뀌었습니다

`applyChanges` 와 읽기 단계는 다시 썼습니다. 매핑은 `insert.length` 를
`insertSize(insert)` 로 바꾼 것이 전부입니다.

**길이 산술이라 무엇이 들어가는지 알 필요가 없습니다.** 좌표계가 경계를
위치로 세고 있었으므로, 경계를 만드는 편집도 그 안에서 그냥 "2 만큼 늘어나는
변경" 입니다. 1단계의 씨앗 200개짜리 성질 테스트가 **생성기도 단언도 그대로**
통과하는 것이 그 증거입니다.

(정확히 하자면 성질 테스트에서도 오라클 한 줄이 같은 이유로 바뀌었습니다 —
`insert.length` → `insertSize(insert)`. `Insert` 가 유니온이 되면서 생긴
타입 문제라 동작은 그대로입니다. 옛 오라클을 되돌려 놓고 타입만 우회해
돌려도 세 성질이 전부 통과합니다.)

설계가 옳았다는 증거는 새 기능이 되는 것보다 **안 고쳐도 되는 코드가
어디까지인가**로 드러납니다.

## 두 겹으로 깎습니다

읽기는 문단 단위로 앞뒤 공통 부분을 걷어낸 뒤, 남은 구간의 머리와 꼬리에서
**글자 단위로 한 번 더** 깎습니다.

두 번째 깎기가 없으면 문단이 하나만 달라져도 변경이 통째로 커집니다.
텍스트는 그래도 맞는데 커서 예측이 무너집니다 — `mapPos` 의 ③번(지워진
구간 안은 경계로 접힘)에 걸리기 때문입니다.

```
Backspace 로 두 문단을 합칠 때

깎기 전:  1..7 을 지우고 "abcd" 삽입     → 커서 예측 5, 실제 3   ✗
깎은 뒤:  3..5 를 지우고 아무것도 안 넣음  → 커서 예측 3, 실제 3   ✓
```

깎은 쪽은 **경계 토큰 두 개만 지웁니다.** 그게 "문단을 합친다" 의 정확한
표현입니다.

## 무작위 편집 열이 약했습니다

종료 조건으로 씨앗 고정 편집 열을 브라우저에 먹이는 테스트를 썼는데,
처음 판은 **글자 단위 깎기를 통째로 지워도 통과했습니다.**

커서가 늘 마지막 편집 자리에 붙어 있어서 Enter 는 문단 끝에서만,
Backspace 는 방금 만든 빈 문단에서만 일어났기 때문입니다. 그 조합은
깎든 안 깎든 커서 예측이 우연히 일치합니다.

커서를 무작위로 옮기는 한 줄을 넣자 바로 어긋나기 시작했습니다.
**무작위 열이라고 다 센 게 아닙니다** — 무엇이 흔들리는지를 봐야 합니다.

## 그리고 2단계의 한계가 드러났습니다

강해진 편집 열이 곧바로 다른 것을 잡았습니다. 씨앗 셋 중 **둘이 40번 안에**
커서 예측을 틀렸고, 전부 2단계가 "알려진 한계" 로 재 뒀던 그 애매함이었습니다.
같은 글자가 이어질 때 어디에 쳤는지 문자열이 말해 주지 않는 문제입니다.

드문 일이 아니었습니다. 그래서 고쳤습니다 — **브라우저가 보고한 커서를
진단에 섞습니다.**

순수 삽입이면 넣은 글자의 끝이 곧 커서여야 하고, 순수 삭제면 지운 자리가
곧 커서입니다. 안 맞으면 창을 밀되 **밀어도 같은 결과가 되는 동안만**
밉니다. 그래서 보정은 텍스트를 바꾸지 않고 커서만 맞춥니다.

처음엔 삭제 쪽을 한 방향만 다뤘고, 편집 열이 씨앗 1 의 23번째 걸음에서
그 절반을 잡아냈습니다.

## 종료 조건을 너무 일찍 선언했습니다

3단계를 "충족" 으로 선언할 때 편집 열은 **씨앗 셋**이었습니다. 나중에 가설을
다시 세워 보려고 넓혔더니 —

| 사냥 범위        | 결과                                |
| ---------------- | ----------------------------------- |
| 씨앗 3 × 40걸음  | 통과 (이걸로 선언했습니다)          |
| 씨앗 25 × 40걸음 | **8개 실패**                        |
| 씨앗 60 × 60걸음 | 고친 뒤 또 **2개 실패** — 다른 원인 |

두 가지가 나왔고 둘 다 진짜 결함이었습니다.

### 1. 문단 단위에도 같은 애매함이 있었습니다

빈 문단이 양쪽에 똑같이 있으면 문단 단위 훑기가 **편집 지점을 지나칩니다.**
문단 0 끝에서 Enter 를 친 것과 문단 1 앞에서 친 것이 같은 문서를 만들기
때문입니다.

```
doc = ["시작a", ""]   커서 4 (문단 0 끝) 에서 Enter
dom = ["시작a", "", ""]

진단:  from=6  ✗      실제: from=4
```

글자 단위에서 커서로 고친 것과 **똑같은 애매함이 한 층 위에** 있었습니다.
3단계 때 "구조 쪽에도 있다" 고 적어만 두고 넘어갔던 것이 그것입니다.
같은 기법을 한 층 위에 썼습니다 — 앞부분 훑기를 커서가 있는 문단에서 멈춥니다.

### 2. 아무 일도 안 일어난 `beforeinput` 이 다음 편집을 망깁니다

브라우저는 `beforeinput` 을 보내 놓고 **아무것도 안 바꾸기도 합니다** —
문서 맨 앞에서 Backspace 가 그렇습니다. 그러면 `input` 이 오지 않아
`flush()` 가 돌지 않고, 적어 둔 커서가 지워지지 않은 채 남습니다.
다음 편집이 그 낡은 값으로 예측합니다.

`caretBefore` 를 "비어 있을 때만 적는다" 로 둔 것이 원인이었습니다.
그 규칙은 조합 중에만 필요합니다.

### 남는 교훈

**무작위 열의 크기가 곧 주장의 크기입니다.** 씨앗 셋으로 통과한 것을
"종료 조건 충족" 이라고 부른 것이 잘못이었습니다. 지금은 스무 개를 상시로
돌리고, 넓은 사냥에서 나온 둘은 **결정론적 테스트로 고정**해 뒀습니다 —
같은 것을 다시 무작위에 맡기지 않으려고요.

## 검증

- **고장 심어 확인** — 글자 단위 깎기를 지우면 노드 7 · 브라우저 9 개 실패,
  커서 보정을 끄면 노드 3 · 브라우저 3 개 실패, 문단 단위 보정을 지우면
  브라우저 8 개 실패, 낡은 커서 수정을 되돌리면 브라우저 1 개 실패
  (마지막 것은 씨앗 스물로는 안 잡힙니다 — 그래서 결정론적 테스트가 지킵니다)
- **구조 변경 성질 테스트** — 씨앗 300개. 1단계 생성기는 글자만 넣어서
  구조 변경을 **한 번도 만들지 않았고**, 그래서 3단계의 핵심 주장이 손으로
  고른 예시 여덟 개에만 기대고 있었습니다. 문서 전체를 토큰 열로 두는
  오라클로 성질까지 올렸습니다
- **오라클의 순환 제거** — 그 오라클도 처음엔 `insertSize` 를 불러서,
  `insertSize` 가 틀리면 같이 틀렸습니다 (경계 비용을 1 로 고장 내도
  통과했습니다). 매 씨앗마다 `docSize(applyChanges(...))` 와 길이를 맞춰
  실제 문서를 정답지로 삼습니다

  > 이 표의 "브라우저 9" 는 처음에 **6 이라고 적었다가 고친 숫자**입니다.
  > 편집 열을 강화하기 **전에** 재 놓고, 강화한 뒤 다시 재지 않은 채로
  > 문서에 옮겼습니다. 강화된 씨앗 셋이 같은 고장을 함께 잡으므로 6 + 3 = 9
  > 입니다. 계기를 바꿨으면 다시 재야 합니다.

- **왕복** — 진단한 변경을 적용하면 언제나 DOM 과 같아집니다
- **크기 산술** — 진단한 증감이 실제 문서 크기 변화와 맞습니다
- **브라우저가 오라클** — 매 flush 마다 `mapPos` 의 예측과 브라우저의
  실제 커서를 비교합니다

## 하지 않는 것

의도적으로 뺐습니다. 이 목록이 "할 것" 목록보다 중요합니다.

- **DOM 비교 최적화** — 매번 통째로 새로 그립니다. 그래서 커서가 죽고,
  그래서 매핑이 필요하다는 게 드러납니다
- **구조 변경에서의 마크** — 지워지는 범위 밖만 살립니다. 정확히 옮기려면
  마크도 조각열로 들고 다녀야 합니다 (ProseMirror 의 `Slice` 가 그렇습니다)
- **마크 편집** — 모델과 렌더는 굵게·기울임을 다루지만 브라우저의
  서식 명령(⌘B)은 읽지 않습니다
- **`openStart`/`openEnd` 깊이** — 양끝이 열린 조각열만 다룹니다.
  붙여넣기를 제대로 하려면 깊이가 필요합니다
- **undo** — 매핑의 *소비자*라, 매핑이 되면 원리는 이미 손에 있습니다
- **`compose`** — 변경 둘을 하나로 접기. 협업에 필요하고, 지금은 순차 적용으로 충분
- **표·이미지·목록**, 플러그인, UI 툴킷

## 종료 조건

**미리 못박아 둔 것입니다.** 학습 스파이크는 목표가 흐려서 썩습니다.

> 무작위 편집 열에 대해 오라클과 일치하고, 브라우저에서 한 문단 쓰는 동안
> 커서가 살아남으면 **멈추고 문서로 정리한다.** (1·2단계)
>
> 문단을 만들고 지우는 동안 모델과 DOM 이 갈라지지 않고 커서가 살아남으면
> 멈춘다. (3단계)

**3단계는 한 번 잘못 선언했다가 다시 세웠습니다.** 씨앗 셋으로 통과한 것을
충족이라고 불렀고, 넓혀 보니 아니었습니다. 지금은 씨앗 스물 + 결정론적
회귀 테스트 위에서 다시 충족입니다. 그 과정이 위 "종료 조건을 너무 일찍
선언했습니다" 에 있습니다.

배우려던 것 — 불변 문서가 매핑을 강제한다, 진실을 모델에 두면 브라우저와
화해해야 한다, 구조를 다루는 것은 좌표계가 아니라 변경의 표현이다 — 을
손으로 겪었으므로 여기서 멈춥니다.

## 이 스파이크가 **증명하지 않은** 것

주장을 넓히지 않으려고 적어 둡니다.

- **크롬만 쟀습니다.** IME 표도 `cancelable` 도 chromium 하나에서 나온
  사실이고, 파이어폭스·사파리는 안 봤습니다
- **진짜 IME 가 아닙니다.** CDP 로 렌더러의 조합 상태를 만든 것이라 합성
  이벤트보다는 훨씬 낫지만, 실제 OS 한글 입력기는 아닙니다
- **"입력을 가로채는 설계가 무너진다" 는 직접 안 봤습니다.** 조합을
  `preventDefault` 로 못 막는다는 **전제**를 쟀을 뿐, 그 설계를 만들어
  실패시킨 적은 없습니다
- **"매핑 없이는 못 쓴다" 는 이 렌더 전략에서만입니다.** 매번 통째로 다시
  그리기 때문에 커서가 죽습니다. ProseMirror 처럼 DOM 을 비교해 최소로
  고치면 결론이 달라질 수 있습니다
- **`mapPos` 가 안 바뀐 것은 확장 한 번의 이야기입니다.** 좌표계도 확장도
  제가 골랐으므로, 설계가 옳았다는 일반 증거는 아닙니다

## 돌리기

```bash
# 모델·매핑·진단 — 노드, 빠름
npx vitest run --root spike/doc-model

# 브라우저가 필요한 것 — IME, 캐럿, 화해 고리
npx vitest run --root spike/doc-model -c vitest.browser.config.ts
```

jsdom 으로는 브라우저 쪽을 잴 수 없습니다. IME 조합, `beforeinput` 의
`cancelable`, 네이티브 캐럿은 전부 실제 렌더러의 동작이고 흉내로는 거짓
결론이 나옵니다.

playwright 가 기대하는 chromium 빌드와 설치된 것이 다른 환경이라면
실행 파일 경로를 넘겨 주면 됩니다.

```bash
CHROMIUM_PATH=/opt/pw-browsers/chromium npx vitest run --root spike/doc-model -c vitest.browser.config.ts
```
