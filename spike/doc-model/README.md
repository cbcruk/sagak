# 1단계 — 위치 매핑

목적은 하나입니다.

> **불변 문서를 택하는 순간 위치 매핑이 의무가 된다는 것을 손으로 겪기.**

`reference-codemirror-state.md` 가 _"불변이라는 선택이 매핑·구조적 공유라는
다음 선택을 강제한다"_ 고 적어 둔 문장을 코드로 확인합니다.

## 성공 기준

"에디터가 돌아감" 이 **아닙니다.** 목표는 특정 실패를 겪는 것입니다 —
`test/why-mapping.test.ts` 가 그것입니다.

```
편집 두 번을 적용할 때, 원래 좌표를 그대로 쓰면 엉뚱한 자리에 들어간다.

  "hello world"  →  "hello" 를 "hi" 로  →  위치 7 에 "big " 삽입
  매핑 없이:  <p>hi worbig ld</p>    ← 틀림
  매핑하고:  <p>hi big world</p>     ← 맞음
```

## 좌표계

ProseMirror 와 같습니다. 위치는 글자가 아니라 **글자 사이의 틈**이고,
**문단의 여닫는 지점도 위치를 하나씩 먹습니다.**

```
doc = [P("ab"), P("cd")]

0     1  2  3     4     5  6  7     8
<p>   a  b  </p>  <p>   c  d  </p>
```

경계가 위치를 먹는 게 처음엔 낭비 같지만, 없으면 "문단 사이" 를 가리킬
방법이 사라집니다. 문단을 새로 넣거나 두 문단을 합치는 편집이 전부 그 자리를
지목해야 합니다.

## `assoc`

위치가 삽입 지점에 **정확히 걸쳤을 때** 앞뒤 어디에 붙을지. 인자 하나지만
나중에 넣으려면 호출부를 전부 다시 봐야 해서 처음부터 넣었습니다.

|      |                                                       |
| ---- | ----------------------------------------------------- |
| `1`  | 삽입된 글자 **뒤** — 타이핑하는 커서                  |
| `-1` | 삽입된 글자 **앞** — 앞에 고정된 표식, 마크 시작 경계 |

빼놓으면 매핑이 "돌아가는데" 커서가 이상하게 굽니다. `test/assoc.test.ts`.

## 검증 — 독립 오라클

`mapPos` 는 자료구조 위의 산술이라 예시 테스트로는 부족합니다. 그래서
문단 텍스트를 **문자 배열이 아니라 id 배열**로 두고 변경을 적용한 뒤,
"원래 `t` 번째 글자가 지금 어디 있나" 를 `indexOf` 로 직접 구합니다.
`mapPos` 와 완전히 독립된 답이라 서로 검산이 됩니다.

씨앗 200개로 돌리고, 실패하면 씨앗이 출력되어 재현됩니다.
(`fast-check` 를 쓰면 반례 축소까지 되지만 의존성을 늘리지 않았습니다.)

**세 가지 고장을 심어 실제로 잡히는 것을 확인했습니다** — `assoc` 무시(1개
실패), 삭제 길이 누락(4개), 접힘 지점 한 칸 밀림(2개).

# 2단계 — `contenteditable` 과 화해하기

`contenteditable` 을 안 쓰겠다는 게 아닙니다. ProseMirror 도 CodeMirror 도
씁니다 — IME 조합, 네이티브 캐럿, 모바일 키보드, 스크린 리더를 포기할 수
없기 때문입니다.

차이는 **누가 진실이냐** 입니다.

|          | 진실 | `contenteditable` 의 역할 |
| -------- | ---- | ------------------------- |
| sagak    | DOM  | 편집 그 자체              |
| PM · CM6 | 모델 | 입력 수단 + 렌더 대상     |

그래서 화살표를 뒤집습니다.

```
beforeinput   막지 않습니다. 커서 위치만 적어 둡니다
     ↓        브라우저가 DOM 을 고칩니다
input         DOM 을 읽어 변경 목록을 만듭니다   (read-dom.ts)
     ↓        모델에 적용합니다                  (change.ts)
     ↓        모델로 DOM 을 다시 그립니다        (view.ts)  ← 네이티브 선택이 죽습니다
     ↓        mapPos 로 커서를 되살립니다        (map.ts)
```

## 성공 기준

1단계 README 가 못박아 둔 종료 조건의 뒷부분입니다.

> 브라우저에서 **한 문단 쓰는 동안 커서가 살아남으면** 멈추고 문서로 정리한다.

`test/reconcile.browser.test.ts` 가 그것입니다.

## 재고 나서 바뀐 것 — IME

1단계 README 에 이렇게 적어 뒀습니다.

> 조합 중인 입력은 `preventDefault` 로 막을 수 없어서…

**결론은 맞았고 이유는 틀렸습니다.** 그건 잰 게 아니라 아는 척한 것이라
2단계의 첫 일로 실제로 쟀습니다 (`test/composition.browser.test.ts`).
CDP `Input.imeSetComposition` 으로 렌더러의 진짜 조합 상태를 만들어
ㅎ→하→한 을 칩니다. 합성 `CompositionEvent` 를 dispatch 하는 건 내 코드가
내 코드를 확인하는 것이라 의미가 없습니다.

크롬이 실제로 하는 말:

| 이벤트                                | `cancelable` | 막으면?      |
| ------------------------------------- | ------------ | ------------ |
| `beforeinput` `insertText`            | `true`       | **막힙니다** |
| `compositionstart`                    | `true`       | 안 막힙니다  |
| `compositionupdate`                   | `true`       | 안 막힙니다  |
| `compositionend`                      | `true`       | 안 막힙니다  |
| `beforeinput` `insertCompositionText` | `false`      | 안 막힙니다  |

조합 이벤트 셋이 전부 취소 가능하다고 **거짓말합니다.** 표준은
`compositionupdate`/`end` 를 취소 불가로 정의하는데도 그렇습니다.
`cancelable` 을 보고 설계하면 틀린다는 뜻이고, 정직한 신호는
`beforeinput` 의 `insertCompositionText` 하나뿐입니다.

전부 `preventDefault` 해도 `한` 은 들어갑니다. 그래서 남는 길은 하나 —
**놔두고, 읽고, 화해시키기.**

부수적으로 나온 사실 하나: `compositionend` 는 **마지막 `input` 뒤에**
옵니다. "조합이 끝나면 `input` 이 한 번 더 오겠지" 하고 기다리는 설계는
그대로 멈춥니다. `EditorView` 가 `compositionend` 에서 직접 flush 하는
이유입니다.

## 매핑이 장식이 아니라는 증거

`renderDoc` 은 문단을 통째로 새로 만듭니다 (ProseMirror 의 DOM 비교
최적화를 일부러 뺐습니다). 그러면 글자 하나 칠 때마다 캐럿이 붙어 있던
텍스트 노드가 사라집니다.

대조군으로 커서 복원을 끄고 `hello` 를 쳐 봤습니다.

```
<p>olleh</p>
```

**글자가 뒤집힙니다.** 다시 그릴 때마다 캐럿이 문단 맨 앞으로 돌아가서
다음 글자가 앞에 붙기 때문입니다. 매핑이 없으면 에디터가 "조금 이상해지는"
게 아니라 아예 못 씁니다.

반대로 매핑이 제대로 붙으면 `mapPos` 의 예측이 **브라우저가 실제로 옮긴
커서와 일치합니다.** 1단계의 id 배열 오라클과 같은 역할을 브라우저가
해 줍니다.

(`writeCaret` 이 항상 위치 1 을 반환하도록 고장 내 보면 10개 중 6개가
실패합니다. 통과가 우연이 아닌지 확인한 것입니다.)

## 알려진 한계 — 진단의 애매함

`read-dom.ts` 는 문자열 둘의 앞뒤 공통 부분을 깎아 차이를 구합니다.
같은 글자가 이어지면 **어디에 쳤는지 문자열만 봐서는 알 수 없습니다.**

`"aaa"` 의 맨 앞에 `a` 를 쳐도 맨 뒤에 넣은 것으로 진단합니다. 텍스트는
어느 쪽으로 봐도 맞으므로 **모델은 멀쩡하고 커서 예측만 어긋납니다.**
그래서 조용합니다 — 브라우저가 보고한 자리라는 정답지가 없었다면 못 찾았을
종류의 버그입니다.

ProseMirror 가 진단에 선택 위치를 섞는 이유가 이것입니다. 재 두기만 하고
고치지 않았습니다 (`reconcile.browser.test.ts`).

## 하지 않는 것

의도적으로 뺐습니다. 이 목록이 "할 것" 목록보다 중요합니다.

- **구조 변경** — Enter, 문단을 가로지르는 삭제, 붙여넣기. 읽기 단계에서
  거부하고 DOM 을 모델로 되돌립니다. 조용히 갈라지는 것보다 눈에 보이게
  실패하는 편이 낫습니다. 3단계의 주제
- **DOM 비교 최적화** — 매번 통째로 새로 그립니다. 그래서 커서가 죽고,
  그래서 매핑이 필요하다는 게 드러납니다
- **마크 편집** — 모델과 렌더는 굵게·기울임을 다루지만 브라우저의
  서식 명령(⌘B)은 읽지 않습니다
- **undo** — 매핑의 *소비자*라, 매핑이 되면 원리는 이미 손에 있습니다
- **`compose`** — 변경 둘을 하나로 접기. 협업에 필요하고, 지금은 순차 적용으로 충분
- **표·이미지·목록**, 플러그인, UI 툴킷

## 종료 조건

**미리 못박아 둔 것입니다.** 학습 스파이크는 목표가 흐려서 썩습니다.

> 무작위 편집 열에 대해 오라클과 일치하고, 브라우저에서 한 문단 쓰는 동안
> 커서가 살아남으면 **멈추고 문서로 정리한다.**

둘 다 충족했습니다. 3단계로 갈지는 별개 판단입니다.

## 돌리기

```bash
# 1단계 + 진단 — 노드, 빠름
npx vitest run --root spike/doc-model

# 2단계 — 진짜 크롬이 필요합니다
npx vitest run --root spike/doc-model -c vitest.browser.config.ts
```

jsdom 으로는 2단계를 잴 수 없습니다. IME 조합, `beforeinput` 의
`cancelable`, 네이티브 캐럿은 전부 실제 렌더러의 동작이고 흉내로는 거짓
결론이 나옵니다.

playwright 가 기대하는 chromium 빌드와 설치된 것이 다른 환경이라면
실행 파일 경로를 넘겨 주면 됩니다.

```bash
CHROMIUM_PATH=/opt/pw-browsers/chromium npx vitest run --root spike/doc-model -c vitest.browser.config.ts
```
