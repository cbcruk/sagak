# 선택 영역 상태를 어떻게 나눌 것인가 — preact 를 살리는 방향

`alignment-buttons.tsx` 의 이 `useEffect` 에서 출발합니다.

```ts
useEffect(() => {
  document.addEventListener('selectionchange', updateAlignment)
  const unsubStyle = eventBus.on(CoreEvents.STYLE_CHANGED, 'after', updateAlignment)
  const unsubRestore = eventBus.on(CoreEvents.CONTENT_RESTORED, 'after', updateAlignment)
  return () => { /* 셋 다 해제 */ }
}, [eventBus, updateAlignment])
```

## 1. 지금 상태 — 같은 블록이 여섯 벌

같은 세 소스(`selectionchange`, `STYLE_CHANGED`, `CONTENT_RESTORED`)를 여섯 곳이
각자 구독합니다.

`alignment-buttons`, `list-buttons`, `link-dialog`, `table-dialog`,
`image-dialog`, `use-font-state`.

문제는 반복 자체보다 **가드가 제각각**이라는 것입니다.

| | IME 가드 | 에디터 범위 확인 | rAF 지연 |
|---|---|---|---|
| `use-font-state` | O | O | O |
| `alignment-buttons` | X | O | X |
| `list-buttons` | X | O | X |
| `link-dialog` | X | X | O |
| `table-dialog` | X | X | O |
| `image-dialog` | X | X | O |

세 가지를 다 갖춘 건 하나뿐입니다. 나머지는 조합이 전부 다릅니다.

**그리고 올바른 버전은 이미 core 에 있습니다.** `EditorCore.setupFormattingStateTracking()`
이 IME 가드 + rAF + 범위 확인을 갖추고 `FORMATTING_STATE_CHANGED` 를 발행합니다.
다만 그 페이로드는 굵게/기울임 같은 인라인 서식뿐이라, 정렬·목록·링크·표·이미지를
보려는 컴포넌트는 각자 다시 만들었습니다.

## 2. 비용 — 측정값

캐럿이 한 번 움직일 때 무슨 일이 벌어지는지 세어 봤습니다. 각 파생 함수는
`window.getSelection()` 으로 시작하므로 그 호출 수를 지표로 씁니다.

| | `getSelection` 호출 |
|---|---|
| `selectionchange` 1회 (평상시) | **21회** |
| `selectionchange` 1회 (한글 조합 중) | **8회** |

**21회.** 여섯 구독자가 각자 DOM 을 훑고, 일부는 조상 체인을 끝까지 올라갑니다.

### 가설이 반쯤 틀렸습니다

"IME 가드가 없으니 조합 중에도 전부 돈다" 고 예상했는데, 재보니 **38%**(8회)만
돕니다. 가드를 가진 `use-font-state` 와 core 의 추적이 빠지기 때문입니다.
남은 8회가 가드 없는 다섯 구독자입니다.

한글 한 글자를 조합하는 동안 keystroke 마다 8번씩 선택 영역을 훑습니다. 심각한
버그는 아니고 — 파생값이 안 바뀌면 preact 가 리렌더를 건너뛰므로 화면은 멀쩡합니다 —
**낭비이고, 무엇보다 규약이 없다는 신호**입니다.

## 3. 선택지

### A. 공유 훅 하나 (의존성 없음)

`useSelectionDerived(derive)` 같은 훅을 만들어 구독·가드·rAF 를 한 곳에 두고,
컴포넌트는 파생 함수만 넘깁니다.

- 가드 불일치가 사라집니다. 규약이 한 곳에 생깁니다.
- 구독은 여전히 컴포넌트 수만큼이지만 (훅이 각자 `useEffect` 를 걸므로),
  공통 소스를 모듈 수준에서 한 번만 구독하도록 짜면 1개로 줄일 수 있습니다.
- 파생 계산 자체는 그대로 6회 — 각자 다른 것을 계산하므로 줄지 않습니다.
- **비용 0.** 새 개념도, 번들 증가도 없습니다.

### B. `@preact/signals` (권장)

preact 가 내놓은 답입니다. 선택 영역을 신호 하나로 두고, 파생값을 `computed` 로
만듭니다.

```ts
const selectionVersion = signal(0)      // 가드를 통과한 변경만 여기서 올립니다
const alignment = computed(() => { selectionVersion.value; return getCurrentAlignment() })
const listType  = computed(() => { selectionVersion.value; return getCurrentListType() })
```

- **구독 1개.** 소스 세 개를 모듈 수준에서 한 번만 구독합니다.
- **파생은 지연 평가됩니다.** `computed` 는 실제로 읽힐 때만 계산합니다. 다이얼로그가
  닫혀 있으면 그 파생은 아예 돌지 않습니다 — 지금은 6개가 무조건 다 돕니다.
- **리렌더가 좁아집니다.** 값이 바뀐 컴포넌트만 다시 그립니다. JSX 안에서 신호를
  직접 읽으면 컴포넌트 렌더를 건너뛰고 텍스트 노드만 갱신합니다.
- `useEffect` + `useState` 조합이 컴포넌트에서 사라집니다.

**비용:** `@preact/signals` + `signals-core` 합쳐 **약 3.7 KB gzip**. 현재 앱 번들이
gzip 59 KB 이므로 6% 증가입니다. preact 10.28 은 peer 요구(`>= 10.25`)를 만족합니다.

### C. core 의 `FORMATTING_STATE_CHANGED` 확장

이미 있는 중앙 추적의 페이로드에 정렬·목록·링크 여부를 더합니다.

- 가드가 이미 올바릅니다. 새 개념이 없습니다.
- 다만 **core 가 UI 가 무엇을 보고 싶은지 알아야 합니다.** 표·이미지처럼 UI 사정인
  것까지 core 페이로드에 넣으면 경계가 흐려집니다. `docs/event-bus-refactor.md` 에서
  줄여 온 방향과 반대입니다.

## 4. 판단

**B 를 권합니다.** 이유는 번들이나 유행이 아니라 **지연 평가**입니다.

지금 구조의 진짜 낭비는 "여섯 번 구독한다" 가 아니라 **"닫혀 있는 다이얼로그 5개가
캐럿이 움직일 때마다 DOM 을 훑는다"** 입니다. 표 다이얼로그가 닫혀 있어도
`findTableAtSelection()` 이 돕니다. 이건 훅으로 묶어도 그대로입니다 —
`computed` 의 지연 평가만이 없앱니다.

A 는 가드 불일치를 고치지만 21회는 그대로입니다. B 는 둘 다 해결합니다.

다만 **A 를 먼저 해도 손해가 아닙니다.** 가드를 한 곳에 모으는 작업은 B 로 갈 때도
그대로 쓰이고, 신호를 도입하지 않기로 해도 남습니다.

### 하지 말아야 할 것

`21회` 를 이유로 성능 문제라고 말하지 않습니다. 재보면 캐럿 이동 한 번에
21회이고, 그게 체감 지연으로 이어진다는 근거는 아직 없습니다. **정리해야 할
이유는 규약이 여섯 갈래로 갈라져 있다는 것이고**, 성능은 따라오는 것입니다.

## 5. 밟을 순서

1. **가드를 한 곳으로** (A) — 여섯 벌의 구독을 공유 훅으로 모으고 IME·범위·rAF 를
   통일합니다. 테스트로 조합 중 훑기가 0 이 되는 것을 고정합니다.
2. **신호 도입** (B) — `@preact/signals` 를 넣고 파생을 `computed` 로 옮깁니다.
   닫힌 다이얼로그의 파생이 돌지 않는 것을 테스트로 고정합니다.
3. **측정** — 1·2 각각에서 `getSelection` 호출 수를 다시 재고 노트에 남깁니다.

각 단계는 따로 머지할 수 있고, 2 를 안 하기로 해도 1 은 남습니다.

## 6. 1단계 실행 결과 — 예측보다 약합니다

`useSelectionDerived` 하나로 여섯 벌의 구독을 모았습니다. 가드는
`EditorCore.setupFormattingStateTracking()` 과 같은 순서(IME → rAF → 범위)를 따릅니다.

| | 전 | 후 |
|---|---|---|
| 구독 (UI) | 6벌, 가드 제각각 | **1벌, 규약 하나** |
| `getSelection` / 이벤트 | 21회 | **18회** |
| 조합 중 (UI) | 8회 | **0회** |
| 선택이 에디터 밖일 때 | 파생 6개 실행 | **실행 안 함** |

### 21 → 18 밖에 못 줄인 이유

§2 를 쓸 때 "21회는 여섯 구독자가 각자 DOM 을 훑기 때문" 이라고 적었는데,
**절반만 맞았습니다.** 호출자를 스택으로 추적해 보니 대부분이 다른 곳이었습니다.

| 호출자 | 이벤트당 |
|---|---|
| core `CommandRegistry.queryState` (굵게·기울임 등 조회) | 6 |
| core `CommandRegistry.queryValue` | 4 |
| UI 파생 6개 | 6 |
| core `isSelectionInEditor` + `wysiwyg-area` 핸들러 | 2 |

**UI 는 21 중 6~7 이었습니다.** 나머지는 core 의 서식 추적입니다. 1단계는 UI 만
건드렸으니 총량이 크게 줄 리가 없었습니다.

§2 에서 "21회를 성능 문제라고 말하지 않는다" 고 선을 그어둔 게 다행이었습니다.
성능을 목표로 삼았다면 이 결과는 실패로 보였을 것입니다. **목표는 규약 통일이었고
그건 달성했습니다.**

### 2단계 예상도 낮춰야 합니다

`computed` 의 지연 평가로 "닫힌 다이얼로그 5개가 안 돈다" 는 이득은 여전히
유효하지만, 그 5개가 이벤트당 **5회** 라는 걸 이제 알았습니다. 21 → 13 이 아니라
**18 → 13** 입니다. core 의 10회는 신호를 도입해도 그대로입니다.

신호가 정말로 큰 이득이 되려면 core 의 `queryState` 조회까지 지연 평가로 바꿔야
하는데, 그건 UI 의 결정이 아닙니다.

### 덤으로 고친 것

- **`useFontState` 가 `CONTENT_RESTORED` 를 구독하지 않고 있었습니다.** 되돌리기
  뒤에 폰트 표시가 갱신되지 않았습니다. 공유 추적기가 세 소스를 다 구독하므로
  자동으로 고쳐졌습니다.
- **다이얼로그 3개(링크·표·이미지)에 범위 확인이 없었습니다.** 선택이 에디터
  밖으로 나가도 파생을 다시 계산해, 툴바 버튼을 누르는 순간 켜짐 상태가
  꺼졌습니다.
- `useFontState` 가 `{fontFamily, fontSize}` 객체를 통째로 `setState` 하고
  있었습니다. 값이 같아도 매번 새 객체라 리렌더가 걸렸습니다. 둘로 나눴습니다.

### 검증

`test/selection-tracking.browser.test.tsx` 3개로 고정했습니다. 각 가드를 하나씩
제거해 **실제로 실패하는 것을 확인**했습니다 — IME 가드 제거 시 조합 중 0 → 11,
범위 확인 제거 시 에디터 밖 4 → 10.2.

기존 검증도 그대로 통과합니다 (ui 35 → 38).

## 7. 성능 재검토 — 문제가 아닙니다

§2·§6 에서 `getSelection` **호출 횟수**를 지표로 썼습니다. 그건 시간이 아닙니다.
다시 재봤습니다.

### 실측

| 문서 크기 | `selectionchange` 1회 처리 시간 |
|---|---|
| 노드 16개 | **0.022ms** |
| 노드 1501개 | **0.015ms** |

프레임 예산 16.7ms 의 **1/1000** 입니다. 문서가 100배 커져도 늘지 않습니다 —
파생 함수들이 캐럿의 조상만 훑기 때문에 문서 전체 크기와 무관합니다.

노드 1501개 문서에 타이핑하며 잰 값:

```
타이핑 총 시간        148ms
프레임 간격 p50/p95   16.7ms / 18.0ms
가장 긴 프레임        18.0ms
긴 작업(50ms+)        0건
```

**성능 문제가 없습니다.** §2 에서 "21회를 성능 문제라고 부르지 않는다" 고
적어둔 판단이 맞았고, 이제 숫자가 뒷받침합니다.

### 이 재검토에서 두 번 틀렸습니다

**첫 번째 — 프레임 대기를 작업 시간으로 착각했습니다.** `selectionchange` 를
쏘고 `requestAnimationFrame` 까지 기다린 시간을 쟀더니 문서 크기와 무관하게
16.7ms 가 나왔습니다. 그건 vsync 간격이지 처리 시간이 아니었습니다.

**두 번째 — 앱이 쓰지도 않는 경로를 쟀습니다.** `document.queryCommandState` 를
직접 재고 "core 의 서식 조회가 전체의 99%" 라고 결론지었습니다. 스파이를 걸어
확인하니 `selectionchange` 10회 동안 레거시 API 호출은 **0회**였습니다.
`CommandRegistry` 의 자체 구현이 우선하므로 레거시는 아예 불리지 않습니다.

두 경로의 차이는 큽니다.

| | 호출당 |
|---|---|
| `document.queryCommandState` (레거시) | 0.137ms |
| `registry.queryState` (자체 구현) | **0.0006ms** |

**약 200배.** `docs/event-bus-refactor.md` 로 이어진 커맨드 레지스트리 작업이
여기서 값을 하고 있었고, 저는 그걸 모른 채 그 아래를 재고 있었습니다.

### 2단계(신호)는 하지 않습니다

`@preact/signals` 의 지연 평가로 없앨 수 있는 것은 **닫힌 다이얼로그 5개의
파생**입니다. 실측하면 그게 `0.001ms × 3 + 0.005ms` 수준입니다.

**3.7 KB gzip 을 써서 0.01ms 를 아끼는 거래입니다.** 하지 않습니다.

§4 에서 "번들이나 유행이 아니라 지연 평가 때문에 권한다" 고 했는데, 그 지연
평가가 아끼는 양을 재보지 않고 말한 것이었습니다. 근거는 측정이 아니라 추론
이었습니다.

### 그러면 1단계는 낭비였나

아닙니다. 다만 **얻은 것이 성능이 아니었을 뿐**입니다.

- 가드 규약이 여섯 갈래에서 하나로 모였습니다.
- 그 과정에서 실제 버그 두 개가 드러났습니다 — `useFontState` 가
  `CONTENT_RESTORED` 를 놓쳐 되돌리기 뒤 갱신이 안 되던 것, 다이얼로그 3개가
  범위 확인이 없어 툴바를 누르면 켜짐 상태가 꺼지던 것.

성능을 목표로 삼았다면 실패였고, 규약을 목표로 삼았으므로 성공입니다.
**목표를 처음에 성능으로 잡지 않은 것이 이 작업에서 제일 잘한 판단입니다.**

### 남긴 것

`test/performance.browser.test.tsx` 두 개. 빠른지를 재는 게 아니라 **비싼 경로가
다시 들어오지 않았는지**를 봅니다. 상한을 실측의 수십 배(1ms)로 잡아 흔들리지
않게 했고, 레거시 폴백으로 되돌아가면(호출당 0.137ms × 8 = 1.1ms) 걸립니다.

## 8. 렌더 측면 — 여기가 100배 큽니다

§7 까지 저는 **파생 비용**(DOM 을 훑는 시간)만 쟀습니다. **렌더 비용**은 한 번도
보지 않았습니다. 재보니 자릿수가 달랐습니다.

### 실측

preact 의 `options.__r`(렌더 시작)·`options.__c`(커밋)에 훅을 걸어 셌습니다.

| 상황 | 렌더 버스트 | 컴포넌트 렌더 | 렌더 시간 |
|---|---|---|---|
| 평범한 글 40자 타이핑 | **0회** | 0 | 0ms |
| 화살표로 커서 이동 30회 | **0회** | 0 | 0ms |
| 캐럿 이동 (파생값 불변) | **0회** | 0 | 0ms |
| **`isBold` 가 한 번 뒤집힘** | 1회 | **195개** | **2.1ms** (p95 4.7ms) |
| 굵게 켜고 끄며 20자 | 16회 | 3120개 | 42.9ms |

파생은 0.02ms 인데 렌더 패스는 **2.1ms** 입니다. 프레임 예산의 12.6% 이고,
§1~§7 에서 제가 매달렸던 것의 **100배**입니다.

### 왜 195개인가

`useFormattingState()` 와 `useHistoryState()` 가 **`Toolbar` 안에** 있습니다.
`isBold` 가 하나 바뀌면 `Toolbar` 가 다시 그려지고, 그 아래 30개 자식과
그들의 아이콘·kinu 내부 컴포넌트까지 전부 따라갑니다.

불리언 하나에 195개입니다.

### 다만 — 일상 타이핑에서는 0입니다

이게 중요합니다. **평범하게 글을 쓰는 동안에는 렌더가 한 번도 일어나지
않습니다.** 커서를 움직여도 0 입니다. `useSelectionDerived` 의 `Object.is`
비교가 값이 안 바뀌면 리렌더를 막기 때문입니다.

195개가 도는 건 **사용자가 서식을 켜거나 끌 때, 또는 서식 경계를 넘을 때**
입니다. 그때 2.1ms 는 16.7ms 프레임 안에 들어가므로 **체감되지 않습니다.**

그러니 이건 "느리다" 가 아니라 **"불리언 하나에 195개를 그리는 구조"** 입니다.

### 두 가지 고칠 방법

**A. 상태를 잎으로 내리기 (0 KB)**

`useFormattingState()` 를 `Toolbar` 가 아니라 각 Toggle 이 직접 부르게 합니다.
그러면 서식이 바뀔 때 Toggle 4개와 그 아이콘만 다시 그립니다 — 195 → 10 정도로
추정됩니다. 새 의존성도, 새 개념도 없습니다.

한계: Toggle 4개는 자기와 무관한 플래그가 바뀌어도 함께 그려집니다
(`isBold` 가 바뀌면 Italic 도 리렌더).

**B. `@preact/signals` (3.7 KB gzip)**

`isBold` 를 신호로 두고 Bold 토글이 직접 읽습니다. 값이 바뀐 토글 **하나만**
다시 그립니다 — 195 → 1~2. JSX 안에서 직접 읽으면 컴포넌트 렌더조차 건너뛰고
DOM 속성만 갱신합니다.

### 판단

**A 를 먼저 재보기를 권합니다.** 195 → 10 이면 이미 95% 이고 비용이 0 입니다.
거기서 남는 10 을 1~2 로 줄이자고 3.7 KB 를 쓸지는 그때 판단하면 됩니다.

§4 에서 신호를 권했던 근거(닫힌 다이얼로그의 지연 평가)는 §7 에서 무너졌습니다.
**신호를 정당화하는 근거가 있다면 그건 지연 평가가 아니라 이 렌더 그래프입니다.**
근거가 바뀌었으니 결론도 다시 세워야 하고, 그러려면 A 의 실측이 먼저입니다.

### 이 절에서 또 두 번 틀렸습니다

- `settle(6)` 을 포함해 재고 "전환 1회당 33ms" 라고 적을 뻔했습니다. 그건 프레임
  6개 대기(≈100ms)였습니다. §7 에서 똑같은 실수를 하고도 반복했습니다.
- 렌더 패스만 분리해서야 2.1ms 가 나왔습니다.

`await` 가 섞인 구간을 재면 거의 항상 프레임 간격이 답을 덮습니다.
**측정 코드에 `await` 가 있으면 그 결과는 일단 의심해야 합니다.**
