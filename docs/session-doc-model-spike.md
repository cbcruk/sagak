## 2. 세 단계가 각각 무엇을 세웠나

### 1단계 — 매핑은 선택이 아니라 의무입니다

`reference-codemirror-state.md` 가 문장으로 적어 둔 _"불변이라는 선택이
매핑이라는 다음 선택을 강제한다"_ 를 손으로 확인했습니다.

성공 기준을 "에디터가 돌아감" 이 아니라 **특정 실패를 겪는 것**으로 잡은
것이 이 단계의 핵심입니다.

```
"hello world"  →  "hello" 를 "hi" 로  →  위치 7 에 "big " 삽입
매핑 없이:  <p>hi worbig ld</p>    ← 틀림
매핑하고:  <p>hi big world</p>     ← 맞음
```

좌표계는 ProseMirror 와 같게 뒀습니다 — 위치는 글자 사이의 틈이고,
**문단의 여닫는 지점도 위치를 하나씩 먹습니다** (`paraSize = 길이 + 2`).
당시엔 낭비처럼 보였는데, 3단계에서 이 결정이 값을 합니다.

### 2단계 — 차이는 `contenteditable` 을 쓰냐가 아니라 누가 진실이냐입니다

처음에 "contentEditable 을 쓰면 못 배웁니다" 라고 적었다가 **"prosemirror 도
contentEditable 을 쓰는 것 아닌가" 라는 지적을 받고 정정**했습니다. 맞습니다.
PM 도 CM6 도 씁니다 — IME·네이티브 캐럿·모바일 키보드·스크린 리더를 포기할
수 없기 때문입니다.

|          | 진실 | `contenteditable` 의 역할 |
| -------- | ---- | ------------------------- |
| sagak    | DOM  | 편집 그 자체              |
| PM · CM6 | 모델 | 입력 수단 + 렌더 대상     |

이 정정이 2단계의 설계를 바꿨습니다 — "DOM 을 안 쓴다" 가 아니라
**화살표를 뒤집는다** 로.

### 3단계 — 울타리를 친 것은 좌표계가 아니라 변경의 표현이었습니다

1·2단계가 "한 문단 안" 에 갇혀 있던 이유는 좌표계가 아니었습니다. 좌표계는
처음부터 경계를 위치로 세고 있었고, **`insert` 가 글자열이라 그 경계를 만들
수도 지울 수도 없었을 뿐**입니다.

`insert` 를 경계를 품는 조각열로 바꾸자 `applyChanges` 와 읽기 단계는 다시
써야 했지만 **`mapPos` 본문은 한 줄만 바뀌었습니다** (`insert.length` →
`insertSize(insert)`).

> 설계가 옳았다는 증거는 새 기능이 되는 것보다 **안 고쳐도 되는 코드가
> 어디까지인가**로 드러납니다.

## 3. 증명을 세 번 잘못했습니다

앞 세션의 교훈이 "계측을 잘못하면 문제 없음이 나온다" 였다면, 이번은
**"증거가 주장의 크기에 못 미쳐도 통과처럼 보인다"** 입니다.

### 3-1. 아는 척한 것을 잰 것처럼 적었습니다 → 이유가 틀렸습니다

1단계 README 에 이렇게 미리 적었습니다.

> 조합 중인 입력은 `preventDefault` 로 막을 수 없어서 "입력을 가로채 모델만
> 고친다" 는 설계가 한글 앞에서 무너집니다.

**잰 게 아니라 플랫폼 상식으로 쓴 문장**이었습니다. 스파이크는 그런 걸
확인하는 자리이므로 2단계의 첫 일로 실제로 쟀습니다 — CDP
`Input.imeSetComposition` 으로 렌더러의 진짜 조합 상태를 만들어 ㅎ→하→한.

**결론은 맞았고 이유는 틀렸습니다.**

| 이벤트                                | `cancelable` | 막으면?      |
| ------------------------------------- | ------------ | ------------ |
| `beforeinput` `insertText`            | `true`       | **막힙니다** |
| `compositionstart`                    | `true`       | 안 막힙니다  |
| `compositionupdate`                   | `true`       | 안 막힙니다  |
| `compositionend`                      | `true`       | 안 막힙니다  |
| `beforeinput` `insertCompositionText` | `false`      | 안 막힙니다  |

크롬은 조합 이벤트 셋을 **전부 취소 가능하다고 보고합니다.** 표준이
`compositionupdate`/`end` 를 취소 불가로 정의하는데도 그렇습니다.
`cancelable` 을 근거로 설계하면 틀립니다.

부수 소득: `compositionend` 가 **마지막 `input` 뒤에** 옵니다. "조합이 끝나면
`input` 이 한 번 더 오겠지" 하고 기다리는 설계는 그대로 멈춥니다.

> 합성 `CompositionEvent` 를 dispatch 하는 건 소용이 없습니다 — `cancelable`
> 이 내가 정한 값이라 **내 코드가 내 코드를 확인하는 것**입니다.

### 3-2. 계기를 바꿔 놓고 그 계기로 잰 숫자를 안 고쳤습니다

3단계 README 에 "글자 단위 깎기를 지우면 브라우저 **6개** 실패" 라고 적었는데
실제로는 **9** 입니다.

편집 열을 강화하기 **전에** 재 놓고, 강화한 뒤 다시 재지 않은 채 문서에
옮겼습니다. 강화된 씨앗 셋이 같은 고장을 함께 잡으므로 6 + 3 = 9 입니다.

앞 세션의 3-1(커밋 횟수로 잰 것)과 같은 종류입니다 — 그때는 **잘못된 계기**를
썼고, 이번엔 **바뀐 계기로 다시 재지 않았습니다.**

### 3-3. 무작위 열의 크기가 곧 주장의 크기입니다

이게 이번 세션에서 제일 비싼 교훈입니다. **두 번** 걸렸습니다.

**첫 번째 — 커서가 안 움직였습니다.** 종료 조건으로 쓴 편집 열의 첫 판은
글자 단위 깎기를 **통째로 지워도 통과했습니다.** 커서가 늘 마지막 편집
자리에 붙어 있어서 Enter 는 문단 끝에서만, Backspace 는 방금 만든 빈
문단에서만 일어났고, 그 조합은 깎든 안 깎든 우연히 일치합니다.

커서를 무작위로 옮기는 한 줄을 넣자 바로 어긋났고, 그 즉시 2단계가 "알려진
한계" 로 눕혀 뒀던 진단 애매함까지 잡혔습니다 — 씨앗 셋 중 둘이 40번 안에.
드문 일이 아니었으므로 고쳤습니다(브라우저가 보고한 커서를 진단에 섞기).

**두 번째 — 씨앗이 셋이었습니다.** 그 상태로 "종료 조건 충족" 을
선언했습니다. 나중에 넓혀 보니 —

| 사냥 범위        | 결과                                |
| ---------------- | ----------------------------------- |
| 씨앗 3 × 40걸음  | 통과 (이걸로 선언했습니다)          |
| 씨앗 25 × 40걸음 | **8개 실패**                        |
| 씨앗 60 × 60걸음 | 고친 뒤 **또 2개 실패** — 다른 원인 |

### 3-4. 오라클이 피검사 코드를 부르면 오라클이 아닙니다

3단계의 핵심 주장은 "매핑은 구조 변경을 몰라도 된다" 인데, 1단계 생성기는
`insert: 'x'.repeat(n)` 만 만들어서 **구조 변경을 한 번도 생성하지
않습니다.** 1단계 주장은 성질로 세우고 3단계 주장은 손으로 고른 예시 여덟
개로 세운 셈이었습니다.

문서 전체를 토큰 열로 두는 오라클을 만들어 씨앗 300개로 올렸는데,
**그 오라클이 순환이었습니다** — 자리를 비울 때 `insertSize` 를 불렀기
때문에, 경계 비용을 2 대신 1 로 고장 내도 오라클이 똑같이 틀려서 그대로
통과했습니다.

매 씨앗마다 `docSize(applyChanges(...))` 와 길이를 맞춰 **실제로 만들어진
문서를 정답지로** 삼도록 고쳤습니다.

## 4. 넓힌 사냥이 잡은 진짜 결함 둘

### 4-1. 문단 단위에도 같은 애매함이 있었습니다

빈 문단이 양쪽에 똑같이 있으면 문단 단위 훑기가 **편집 지점을 지나칩니다.**
문단 0 끝에서 Enter 를 친 것과 문단 1 앞에서 친 것이 같은 문서를 만들기
때문입니다.

```
doc = ["시작a", ""]   커서 4 (문단 0 끝) 에서 Enter
dom = ["시작a", "", ""]

진단:  from=6  ✗      실제: from=4
```

글자 단위에서 커서로 고친 것과 **똑같은 애매함이 한 층 위에** 있었고,
3단계 때 "구조 쪽에도 있다" 고 적어만 두고 넘어간 것이 바로 이것입니다.

### 4-2. 아무 일도 안 일어난 `beforeinput` 이 다음 편집을 망깁니다

브라우저는 `beforeinput` 을 보내 놓고 **아무것도 안 바꾸기도 합니다** —
문서 맨 앞에서 Backspace 가 그렇습니다. 그러면 `input` 이 오지 않아 flush 가
돌지 않고, 적어 둔 커서가 지워지지 않은 채 남습니다.

```
s22 jump=1:ok key={Backspace} caretRead=1  flush=none      ← input 이 안 옵니다
s23 jump=7:ok key={Enter}     caretRead=7  predicted=1  ✗  ← 낡은 1 을 씁니다
```

`caretBefore` 를 "비어 있을 때만 적는다" 로 둔 것이 원인이었습니다. 그 규칙은
조합 중에만 필요합니다.

### 공통점 — 전부 텍스트는 맞고 커서만 틀립니다

이번 세션의 결함은 앞 세션의 ASCII 버그들과 실패 방식이 같습니다.
**조용합니다.**

|           | 앞 세션 (ASCII)              | 이번 (커서)            |
| --------- | ---------------------------- | ---------------------- |
| 증상      | "결과 없음" · "아무 일 없음" | 문서는 멀쩡, 커서만 튐 |
| 예외      | 없음                         | 없음                   |
| 발견 경로 | 다른 목적의 작업 중          | 다른 목적의 작업 중    |

찾으러 간 적이 없다는 것까지 같습니다. 이번엔 "가설을 다시 증명해 보자" 가
그 다른 목적이었습니다.

## 5. 이 세션이 남긴 규율

앞 세션의 넷([`session-2026-08.md`](./session-2026-08.md) §4)에 더해서 —

5. **무작위 열의 크기가 곧 주장의 크기입니다.** 씨앗 셋으로 통과한 것을
   "충족" 이라고 부르면 안 됩니다. 넓힐 수 있으면 넓혀 보고, 넓힌 범위를
   같이 적습니다.
6. **무작위가 잡은 것은 결정론적으로 고정합니다.** 같은 것을 다시 무작위에
   맡기면 다음에 안 나올 수 있습니다. 60 × 60 이 필요했던 결함은 씨앗
   스물로는 안 잡힙니다.
7. **오라클이 피검사 코드를 부르면 오라클이 아닙니다.** 둘이 함께 틀리면
   서로 맞아 떨어집니다. 독립된 정답지에 묶어 둬야 합니다.
8. **계기를 바꿨으면 그 계기로 잰 숫자를 전부 다시 잽니다.**
9. **아는 척한 것과 잰 것을 문서에서 구분합니다.** 스파이크는 전자를
   후자로 바꾸는 자리입니다.

## 6. 이 스파이크가 증명하지 **않은** 것

주장을 넓히지 않으려고 [`spike/doc-model/README.md`](../spike/doc-model/README.md)
에도 같은 목록을 뒀습니다.

- **크롬만 쟀습니다.** IME 표도 `cancelable` 도 chromium 하나에서 나온
  사실이고 파이어폭스·사파리는 안 봤습니다
- **진짜 IME 가 아닙니다.** CDP 로 렌더러의 조합 상태를 만든 것이라 합성
  이벤트보다는 훨씬 낫지만 실제 OS 한글 입력기는 아닙니다
- **"가로채는 설계가 무너진다" 는 전제만 쟀습니다.** 그 설계를 만들어
  실패시킨 적은 없습니다
- **"매핑 없이 못 쓴다" 는 이 렌더 전략에서만입니다.** 매번 통째로 다시
  그리기 때문에 커서가 죽습니다. PM 처럼 DOM 을 비교해 최소로 고치면
  결론이 달라질 수 있습니다
- **`mapPos` 가 안 바뀐 것은 확장 한 번의 이야기입니다.** 좌표계도 확장도
  제가 골랐으므로 설계가 옳았다는 일반 증거는 아닙니다

## 7. 열려 있는 것

### 스파이크

**여기서 멈춥니다.** 배우려던 셋을 다 겪었고 종료 조건도 (다시 세워서)
충족했습니다. 이어서 한다면 README 의 "하지 않는 것" 이 다음 목록입니다 —
DOM 비교 최적화, 마크의 조각열화, `openStart`/`openEnd` 깊이, undo, `compose`.

### 본체로 가져올 것

이 스파이크는 **본체에 아무것도 안 넣었습니다.** 가져오려면 별개 판단이
필요하고, 근거는 아직 없습니다. 다만 스파이크가 드러낸 대비는 남습니다 —
본체는 DOM 이 진실이라 `selectionManager.saveSelection()`/`restoreSelection()`
으로 위치를 지키는데, 그건 매핑이 없어서 하는 일입니다.

### 앞 세션에서 넘어온 것

- 원격 브랜치 3개(`claude/find-dialog-effects`, `spike/render-a`,
  `spike/render-b`) — 프록시 403(조직 정책)으로 삭제가 막혀 있습니다
- 중국어 자동 완성 임계값 (설정 문제이지 버그가 아님)
- 커버리지 공백 — 접근성, 모바일·태블릿 뷰포트, 표 크기 조절
