# Phase 8 착수 — 무엇이 먼저인가

> 상태: 진행 중 · 대상: `sagak-core`

## 요약

Phase 8(블록 기반 에디터)의 선행 작업 §8.0 은 끝났고 8.1~8.4 는 미착수입니다.
그런데 `reference-codemirror-state.md` 의 우선순위 표에는 **트리거 조건이 달린
항목이 다섯 개** 있습니다. 착수 지점을 취향으로 고르는 대신 그 조건들이
충족됐는지 재 봤습니다.

| #   | 항목                     | 적힌 트리거         | 지금                 |
| --- | ------------------------ | ------------------- | -------------------- |
| 1   | 엔진 순수화 (Range 주입) | 즉시                | **이미 완료**        |
| 2   | 델타 기반 undo           | 대용량 문서 요구 시 | **아직 아님 — 측정** |
| 3   | 문자소 클러스터          | 오프셋 연산 점검 시 | 미확인               |
| 4   | 원자성 → 트랜잭션        | signals 도입 시     | **확인함 — 보류**    |
| 5   | 델타 인코딩 + assoc      | Phase 8 설계        | 설계 재료            |

## 1. 엔진 순수화 — 이미 돼 있습니다

노트는 "인라인 서식 엔진의 진입 함수가 `window.getSelection()` 을 직접 읽어
전역 selection 에 결합돼 있다" 고 적었지만, 지금은 range-in 변형이 전부
있습니다.

```
applyInlineStyleInRange · applyLinkInRange · removeLinkInRange · toggleFormatInRange
```

전역 selection 을 읽는 것은 그 위의 얇은 셸뿐입니다. **Phase 8 의 엔진 재사용
경로는 이미 확보돼 있습니다.** 노트의 이 항목은 닫아도 됩니다.

## 2. 델타 기반 undo — 측정 결과 아직 아닙니다

노트는 `HistoryManager` 가 스냅샷마다 `innerHTML` 전체를 복사하므로 메모리가
`O(문서 × 깊이)` 라고 적고 "대용량 문서 지원이 요구되는 시점의 1순위" 로 미뤄
두었습니다. 그 시점이 지금인지 브라우저에서 쟀습니다 (`maxSize` 기본값 100).

| 문단 수 | 문서 크기 | 스냅샷 읽기 | undo 쓰기 | 히스토리 100개 |
| ------- | --------- | ----------- | --------- | -------------- |
| 10      | 1 KB      | 0.005 ms    | 0.02 ms   | 0.1 MB         |
| 100     | 11 KB     | 0.080 ms    | 0.20 ms   | 1.1 MB         |
| 500     | 55 KB     | 0.225 ms    | 0.60 ms   | 5.4 MB         |
| 2000    | 222 KB    | 0.925 ms    | 2.76 ms   | 21.6 MB        |

2000문단(222 KB, 원고지 수백 장 분량)에서도 스냅샷은 **0.925 ms**, undo 는
**2.76 ms** 입니다. 둘 다 한 프레임(16.7 ms) 안입니다. 메모리 21.6 MB 는 눈에
띄지만 치명적이지 않고, 그나마 100단계를 꽉 채웠을 때입니다.

또한 스냅샷은 500 ms 디바운스라 **매 키 입력마다 찍히지 않습니다.**

**결론: 트리거는 발동하지 않았습니다.** 델타 undo 는 계속 미룹니다. 다시 볼
조건은 "문서가 1 MB 를 넘거나 히스토리 깊이를 크게 늘려야 할 때" 로 구체화해
둡니다.

## 3. 측정하다 나온 것 — 아무도 안 읽는 문자열을 매번 만들고 있었습니다

위를 재는 김에 타이핑 중 `innerHTML` 직렬화 횟수를 셌습니다.

```
입력 30회 → innerHTML 직렬화 31회
```

디바운스가 500 ms 인데 왜 입력마다 한 번씩인가. 히스토리가 아니라 다른
곳이었습니다.

```ts
// wysiwyg-area.ts — 이전
this.element.addEventListener('input', () => {
  this.eventBus.emit(WYSIWYG_CONTENT_CHANGED, {
    content: this.element.innerHTML, // 매 입력마다 문서 전체 직렬화
  })
})
```

그리고 **구독자 둘 다 이 값을 읽지 않습니다.**

| 구독자             | 핸들러                                         |
| ------------------ | ---------------------------------------------- |
| `EditorCore`       | `updateFormattingState` — 인자를 받지 않습니다 |
| 자동 저장 플러그인 | `() => scheduleSave()` — 페이로드를 버립니다   |

즉 아무도 안 보는 문자열을 키 하나당 한 번씩, 문서 크기에 비례하는 비용으로
만들고 있었습니다. 2000문단이면 0.925 ms 입니다.

게터로 바꿔 **읽을 때** 직렬화하게 했습니다. 계약(`{ content: string }`)은
그대로이고 아무도 안 읽으면 비용이 0 입니다.

```
입력 30회 → innerHTML 직렬화 1회   (남은 1회는 디바운스된 히스토리 스냅샷)
```

**31 → 1.** 회귀는 `wysiwyg-area.browser.test.ts` 가 막습니다 — 페이로드를 읽기
전에는 게터 호출이 0 이어야 하고, 읽으면 그때 제대로 나와야 합니다. 예전
방식으로 되돌리면 `expected 10 to be +0` 으로 걸리는 것을 확인했습니다.

### 이것이 Phase 8 과 무슨 상관인가

이 낭비는 실수가 아니라 **구조의 세금**입니다. 문서 모델이 없으니 "무언가
바뀌었다" 를 알리는 유일한 방법이 문서 전체를 문자열로 만드는 것입니다.
델타가 있으면 바뀐 부분만 실어 보내면 됩니다.

게터는 그 세금을 **미루기만 합니다.** 자동 저장을 켜면 저장할 때마다 다시 전체
직렬화가 돌아옵니다 — 그리고 [#21](https://github.com/cbcruk/sagak/pull/21) 이
찾아낸 대로 꺼져 있던 자동 저장을 **이후 켰습니다.** 다만 저장은 2 초 디바운스라
키 입력당이 아니라 저장당이고, `performSave` 는 페이로드가 아니라 `element` 를
직접 읽으므로 게터 최적화는 그대로 유효합니다.

없애려면 델타가 필요하고, 그것이 항목 5 입니다.

## 4. 원자성/트랜잭션 — 전제를 확인했습니다

노트 §4 는 트리거를 "signals 도입 시" 로 적었고 그것은
[#20](https://github.com/cbcruk/sagak/pull/20) 에서 일어났습니다. 주장은
이랬습니다 — `CAPTURE_SNAPSHOT → 커맨드 → STYLE_CHANGED` 가 별개 이벤트로
흘러 **중간 상태가 관찰될 수 있다**.

관찰 "가능성" 이 아니라 실제로 관찰되는지 재야 합니다. preact 의 커밋 훅
(`options.__c`) 에 붙어, 커밋마다 **화면과 문서를 함께** 찍었습니다.

| 동작            | 커밋 | 화면이 문서와 어긋난 커밋 |
| --------------- | ---- | ------------------------- |
| Bold 클릭       | 2    | **0**                     |
| 자동 완성 APPLY | 1    | **0**                     |
| **Undo**        | 2    | **1**                     |

### 노트가 든 예시는 이미 원자적입니다

§4 가 인용한 것은 자동 완성이었습니다 — "글자는 추가됐는데 팝업이 떠 있는"
중간 상태. 그런 커밋은 없었습니다. 플러그인이 한 핸들러 안에서 동기로 둘 다
하기 때문입니다.

```ts
applyAutocomplete(element, currentPrefix, word)
hideAutocomplete()
```

한 동기 블록 → 한 플러시 → 커밋 1회. CM6 이 트랜잭션으로 얻는 성질을 여기서는
구조상 이미 갖고 있습니다.

> **측정 주의.** 처음에는 `AUTOCOMPLETE_SHOW` 를 직접 발행해 몰았는데 커밋이
> 0회 나왔습니다. `hideAutocomplete()` 가 플러그인 내부 `isAutocompleteVisible`
> 를 보는데 그 플래그를 우회했기 때문입니다 — 측정이 무효였습니다. 플러그인의
> 실제 경로(키업 → 제안)로 다시 몰아서 얻은 숫자가 위 표입니다.

### 실제로 어긋나는 곳은 undo 하나입니다

undo 직후 한 커밋에서 **문서는 굵기가 풀렸는데 툴바는 아직 눌려 있습니다.**

```
1. {"화면_bold": true,  "문서_bold": false}   ← 어긋남
2. {"화면_bold": false, "문서_bold": false}
```

한 프레임(16.7 ms)짜리입니다.

### 그런데 원인은 §4 가 지목한 것이 아닙니다

노트는 이것을 "`batch()` 규율과 트랜잭션 도입의 정확한 동기" 라고 적었습니다.
**둘 다 이 문제를 못 고칩니다.**

확인한 것 —

1. **`batch()` 로는 안 됩니다.** 간극이 같은 틱의 신호 쓰기가 아니라 프레임
   경계입니다. `batch()` 는 같은 틱만 묶습니다.
2. **선택 영역이 죽어서가 아닙니다.** `element.innerHTML` 교체가 선택을
   날린다고 봤지만, `CONTENT_RESTORED` 시점에 재보니
   `{rangeCount: 1, 편집영역안: true}` 였습니다.
3. **데이터가 없어서도 아닙니다.** 같은 시점에 `queryState('bold')` 는 이미
   올바르게 `false` 를 돌려줍니다.
4. **동기로 앞당겨도 안 고쳐집니다.** 서식 계산을 rAF 에서 떼어
   `CONTENT_RESTORED` 에서 바로 발행하도록 두 번(전체 리팩토링 한 번, 최소
   프로브 한 번) 시도했고, **숫자가 전혀 바뀌지 않았습니다** (2커밋 / 1어긋남).
   측정된 이득이 0이라 두 변경 모두 되돌렸습니다.

즉 어긋난 커밋은 서식 발행 **이전에** 일어납니다. 무엇이 그 커밋을 유발하는지는
아직 모릅니다. 이벤트 순서 문제가 아니므로 트랜잭션을 도입해도 그대로일
가능성이 큽니다.

### 판단

**항목 4 는 지금 착수할 근거가 없습니다.**

- 노트가 든 예시는 이미 원자적입니다.
- 남은 것은 undo 경로의 한 프레임짜리 표시 지연 하나이고,
- 그 원인이 원자성이 아니므로 트랜잭션으로 해결되지 않습니다.

이건 Phase 8 의 동기가 아니라 **별도의 작은 버그**로 분리해 다뤄야 합니다.
착수하려면 먼저 "어긋난 커밋을 유발하는 것이 무엇인가" 를 규명해야 합니다 —
그 전까지는 고칠 대상이 특정되지 않습니다.

## 이 노트가 정한 것

1. 항목 1 은 완료로 닫습니다.
2. 항목 2 는 계속 미루되, 재검토 조건을 "문서 1 MB 초과 또는 히스토리 깊이
   증가 요구" 로 구체화합니다.
3. **항목 4 는 근거 부족으로 보류합니다** (§4). 노트가 든 예시는 이미
   원자적이고, 실제 어긋남은 undo 한 프레임뿐이며 그 원인이 원자성이
   아닙니다. undo 표시 지연은 별도 버그로 분리합니다.
4. 항목 3·5 는 열려 있습니다.
5. 8.1(블록 데이터 모델)에는 아직 손대지 않습니다. 근거 없이 시작하면
   `reference-codemirror-state.md` 가 경고한 그대로가 됩니다 — _"불변이라는
   선택이 매핑·구조적 공유라는 다음 선택을 강제한다."_
