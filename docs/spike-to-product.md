# 스파이크 모델을 본체에 적용할 것인가

> 상태: 검토 · 대상: [`spike/doc-model`](../spike/doc-model) → `packages/core`
> 관련: [`session-doc-model-spike.md`](./session-doc-model-spike.md), [`phase-8-entry.md`](./phase-8-entry.md)

## 결론

**모델 전면 적용은 지금 하지 않습니다.** 그런데 "그러니 아무것도 안 한다" 는
아닙니다. 재보니 세 갈래로 갈립니다.

|                               | 판단       | 근거                                              |
| ----------------------------- | ---------- | ------------------------------------------------- |
| 문서 모델 전면 이전           | **안 함**  | 플러그인 33개 중 **2개만** 지금 모델로 표현됩니다 |
| 스파이크가 예측한 결함 고치기 | **함**     | undo 후 캐럿이 문서 맨 앞으로 갑니다 — 실측       |
| 그 고침에 모델이 필요한가     | **아니오** | 필요한 건 모델이 아니라 **좌표**입니다            |

셋째 줄이 이 검토의 핵심입니다. 스파이크에서 수확할 것은 **모델이 아니라
정수 좌표**이고, 그 부분은 모델 없이 떼어 쓸 수 있게 만들어져 있습니다.

---

## 1. 전면 이전의 비용 — 잰 것

### 1-1. 모델이 표현할 수 있는 것 vs 플러그인이 요구하는 것

스파이크 모델은 **문단 + 텍스트 + 굵게/기울임** 이 전부입니다.

```ts
interface Mark {
  type: 'bold' | 'italic'
  from: number
  to: number
}
interface Paragraph {
  text: string
  marks: Mark[]
}
type Doc = Paragraph[]
```

본체 플러그인 33개를 이 모델에 요구하는 것으로 나눠 보면 —

| 모델에 필요한 것     | 플러그인                                                                                              | 수    |
| -------------------- | ----------------------------------------------------------------------------------------------------- | ----- |
| **지금 모델로 됨**   | bold, italic                                                                                          | **2** |
| 마크 종류 추가       | underline, strike, subscript, superscript                                                             | 4     |
| 마크에 **값** (속성) | font-family, font-size, text-color, background-color, letter-spacing, link                            | 6     |
| 문단 **속성**        | heading, paragraph, alignment, indent, outdent, line-height                                           | 6     |
| **새 노드 종류**     | ordered-list, unordered-list, table, table-resize, image, image-resize, image-upload, horizontal-rule | 8     |
| 다시 배선            | find-replace, autocomplete, history, auto-save, export, keyboard-shortcuts, special-character         | 7     |

**33개 중 2개**입니다. 나머지 31개는 모델을 늘려야 하고, 그 중 8개는
스파이크에 아예 없는 **노드 스키마**를 요구합니다 (표는 중첩 구조입니다).

### 1-2. DOM 을 진실로 삼는 표면

| 호출           | 건수 | 파일 |
| -------------- | ---- | ---- |
| `execCommand`  | 56   | 36   |
| `getSelection` | 43   | 18   |
| `innerHTML`    | 26   | —    |
| `createRange`  | 10   | —    |

한 가지 좋은 소식은 있습니다 — `execCommand` 는 **명령 계층에 몰려
있습니다**. 상위 파일이 `legacy-exec-command`(6), `wysiwyg-area`(3),
`default-commands`(3), `commands/*`(각 2~3) 이고, 33개 플러그인 대부분은
`runCommand('bold')` 로 그 계층을 부릅니다. 화살표를 뒤집는다면 손댈 곳은
플러그인이 아니라 **명령 계층 12여 개 파일**입니다.

그래도 표·이미지·목록의 노드 스키마와 렌더러는 별개 비용입니다.

### 1-3. 다시 세워야 할 검증

core 테스트 22,758줄, 브라우저 테스트 파일 56개. **전부 DOM 동작을
단언합니다.** 진실을 모델로 옮기면 이 단언들의 기준이 바뀝니다.

### 1-4. 스파이크가 일부러 안 한 것 중 본체에 필수인 것

- **DOM 비교 최적화** — 스파이크는 매번 통째로 다시 그립니다. 표·이미지가
  있는 문서에서 키 입력마다 통째로 다시 그리면 이미지가 다시 로드되고
  표 크기 조절 상태가 날아갑니다. PM 급의 DOM 비교가 **선택이 아니라 전제**가
  됩니다
- **`openStart`/`openEnd` 깊이** — 붙여넣기를 제대로 하려면 필요합니다
- **스키마·검증** — 어떤 노드가 어디에 올 수 있는지
- **undo** — 스파이크에 없습니다

## 2. 그런데 스파이크가 예측한 결함이 본체에 실제로 있습니다

스파이크 2단계의 대조군은 이랬습니다 — 커서 복원을 끄고 `hello` 를 치면
`<p>olleh</p>` 가 됩니다. **내용을 통째로 갈아끼우면 네이티브 선택이
죽는다**는 것이었습니다.

본체의 undo 가 정확히 그 일을 합니다.

```ts
// packages/core/src/plugins/history-plugin.ts
element.innerHTML = previousState.content
// ...선택 복원은 없습니다
```

**실측했습니다.**

```
UNDO 전  : html="<p>hello brave world</p>"  캐럿 = #text offset 11  ("brave" 뒤)
UNDO 후  : html="<p>hello world</p>"        캐럿 = DIV  offset 0     ← 무너짐
타이핑 후 : html="<p>Xhello world</p>"                               ← 맨 앞에 들어감
```

undo 한 번마다 캐럿이 문서 맨 앞으로 갑니다. 이어서 타이핑하면 **글자가 문서
앞에 붙습니다.** 스파이크의 `olleh` 와 같은 실패 모드이고, 키 입력마다가
아니라 undo 마다 일어나는 것뿐입니다.

기록에 없던 것입니다. 찾으러 간 것도 아니고 "스파이크를 본체에 적용할 수
있나" 를 재다가 나왔습니다 — 이 저장소에서 반복되는 패턴입니다.

### 기존 API 로는 못 고칩니다

본체에는 이미 `selectionManager.saveSelection()`/`restoreSelection()` 이
있습니다. 그런데 —

```ts
private savedRange: Range | null = null
this.savedRange = range.cloneRange()
```

`Range` 는 **노드 참조**입니다. `innerHTML` 을 갈아끼우면 그 노드들이
떨어져 나갑니다. 재봤습니다.

```
addRange(saved) → 예외 없음, rangeCount=1
                  그런데 container=DIV, offset=0   ← 조용히 0 으로 갑니다
```

**예외도 안 납니다.** 그래서 이 API 를 undo 에 갖다 붙여도 증상이 그대로
입니다. 이 API 가 지금 잘 도는 곳(다이얼로그 열고 닫기)은 **노드가 살아남는**
경우뿐입니다.

## 3. 그 고침에 모델은 필요 없습니다

필요한 것은 **노드 참조가 아니라 정수 좌표**입니다. 내용이 갈아끼워져도
"문단 0 의 11번째 글자 뒤" 는 여전히 말이 됩니다.

그리고 스파이크의 그 부분은 **모델을 인자로 받지 않습니다.** 2단계에서
일부러 그렇게 만들었습니다.

```ts
// spike/doc-model/src/view.ts
export function domToPos(
  root: HTMLElement,
  node: Node,
  offset: number
): number | null
export function posToDom(
  root: HTMLElement,
  pos: number
): { node: Node; offset: number } | null
```

DOM 만 보고 정수 위치를 계산합니다. 본체에 필요한 것이 정확히 이것입니다 —
undo 전에 `domToPos` 로 정수를 적어 두고, `innerHTML` 을 갈아끼운 뒤
`posToDom` 으로 되돌리면 됩니다.

### 다만 그대로는 못 씁니다 → **일반화해서 넣었습니다**

스파이크 버전은 `<p>` 만 있는 평평한 구조를 전제합니다. 본체는 표·목록이
중첩되므로 트리를 훑는 판이 필요했습니다.

처음 이 문서를 쓸 때는 **재보지 않았다**고 적어 뒀습니다 — "50줄쯤" 이라고
말하고 싶었지만 그건 아는 척이라서. 이제 만들었고, `core/dom-position.ts`
입니다.

|           |                                                                                          |
| --------- | ---------------------------------------------------------------------------------------- |
| 크기      | 텍스트는 글자 수 · 안이 없는 요소(`br`·`img`·`hr`)는 1 · 그 밖의 요소는 여는 + 안 + 닫는 |
| 왕복 검증 | 본체가 실제로 만드는 구조 13종에서 **모든 위치**가 제자리로 돌아옵니다                   |
| 독립 검증 | `Range.toString()` + `querySelectorAll` 로 센 크기와 일치                                |

**왕복만으로는 부족했습니다.** `<br>` 크기를 1 대신 0 으로 고장 내 보니
왕복 13종이 전부 통과했습니다 — 두 방향이 사이좋게 틀렸기 때문입니다.
스파이크에서 오라클이 순환했던 것과 같은 종류라, 브라우저가 세 주는 값에
따로 묶었습니다. 그 뒤 같은 고장이 5개를 실패시킵니다.

### 더 싼 길도 있습니다

undo 스냅샷에 **캐럿 위치를 같이 저장**하는 것입니다. 스냅샷을 찍는 시점에
`domToPos` 로 정수를 구해 `{ content, caret }` 로 저장하고, 복원할 때 같이
되돌립니다. 좌표 계산이 여전히 필요하지만 **매핑은 필요 없습니다** — 되돌리는
자리가 저장할 때와 같은 문서이기 때문입니다.

매핑(`mapPos`)이 필요해지는 건 **저장한 뒤에 문서가 또 바뀌는** 경우입니다.
협업이나 비동기 편집이 없는 지금은 그 경우가 없습니다.

## 4. 그래서 무엇을 하나

### 지금 할 만한 것 → **했습니다**

**undo/redo 의 캐럿 복원.** 관문이었던 "표·목록이 있는 문서에서도 좌표가
서는지" 를 먼저 재고 착수했습니다.

`HistoryState` 에는 `selection?: { start, end }` 필드가 **선언만 되고
아무도 안 쓰는 채로** 있었습니다. 누군가 예상은 했는데 배선을 안 한
자리입니다. 거기에 정수 위치를 채웁니다.

회귀 테스트는 **고치기 전에 6개 중 5개가 실패**하는 것을 확인하고 썼습니다.
전부 `anchor: 0` — 캐럿이 문서 맨 앞으로 무너지는 그 증상입니다.

비용도 쟀습니다. 스냅샷은 타이핑 경로(디바운스 500 ms)에 있으므로 —

| 문서         | 위치 읽기 | 비교군 (`innerHTML`) |
| ------------ | --------- | -------------------- |
| 문단 200개   | 0.042 ms  | 0.038 ms             |
| 문단 2,000개 | 0.286 ms  | 0.320 ms             |

이미 하고 있던 `innerHTML` 복사와 **같은 자릿수**입니다. 되돌리기 쪽
(`writeSelectionPositions`)은 2,000문단에서 1.3 ms 인데, undo 는 낱개
동작이라 문제되지 않습니다.

### 지금 안 하는 것

**문서 모델 전면 이전.** 33개 중 2개, 노드 스키마 8개, 테스트 22,758줄,
그리고 DOM 비교 최적화가 전제가 됩니다. 배움의 값은 이미 스파이크에서
받았고, 본체에 넣는 값은 아직 서지 않습니다.

### 다시 볼 조건

[`phase-8-entry.md`](./phase-8-entry.md) 의 방식대로 **미리 못박습니다.**
아래 중 하나라도 서면 다시 봅니다.

1. **협업 편집** — 남의 편집이 내 위치를 밀 때. 매핑이 그때 의무가 됩니다.
   지금 없는 유일한 강한 근거입니다
2. **undo 를 델타로** — 문서 1 MB 초과 (앞 세션이 정한 조건). 델타 undo 는
   모델 없이는 못 만듭니다
3. **캐럿 결함이 좌표만으로 안 잡힐 때** — 3번 항목을 하다가 "결국 모델이
   있어야 한다" 로 몰리면 그게 근거입니다

### 안 서는 근거

- "PM/CM6 이 그렇게 한다" — 그들은 협업·플러그인 생태계·거대 문서를 답니다
- "구조가 더 깨끗하다" — 재본 적 없습니다
- "성능" — 지금 병목은 모델 부재가 아닙니다. 앞 세션에서 성능 근거로 착수를
  정당화하려다 트리거 다섯 중 셋이 "아직 아님" 으로 닫혔습니다

## 5. 이 검토가 재지 않은 것

- ~~중첩 구조에서의 좌표 계산 난이도~~ — 만들어서 쟀습니다 (3절)
- **DOM 비교 최적화의 실제 비용** — "전제가 된다" 까지만 말했고 규모는
  모릅니다
- **부분 이전** (본문만 모델로, 표·이미지는 DOM 으로) — 두 좌표계가 공존하는
  설계이고, 그게 더 나은지 나쁜지 안 봤습니다
- **undo 캐럿 결함의 실제 체감도** — 재현은 했지만 사용자가 얼마나 자주
  겪는지는 모릅니다. `history-plugin` 은 500 ms 디바운스라 undo 단위가
  크고, 그만큼 한 번의 캐럿 손실이 크게 느껴질 수도 있습니다
