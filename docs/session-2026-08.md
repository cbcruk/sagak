## 2. ASCII 전제가 만든 버그 셋

같은 뿌리에서 셋이 나왔습니다. JS 의 `\b` 는 `\w`(= `[A-Za-z0-9_]`) 기준이라
**한글 앞뒤에서 성립하지 않습니다.**

| 곳             | 한국어 사용자에게  | PR  |
| -------------- | ------------------ | --- |
| 찾기 단어 단위 | "No matches found" | #25 |
| 자동 완성 사전 | 제안 전무          | #27 |
| 링크 URL 검증  | 링크가 안 걸림     | #29 |

공통점이 둘입니다.

**① 전부 조용히 실패했습니다.** 예외도 경고 배너도 없이 "결과 없음" 이나
"아무 일 없음" 으로 끝나서, 콘솔을 보지 않으면 알 수 없었습니다.

**② 전부 다른 목적의 작업 중에 나왔습니다.** 하나는 Phase 8 트리거 점검,
하나는 "범위 개선", 하나는 잔여 훑기. **찾으러 간 적이 없습니다.**

### 지금 상태

`\b`·`\w`·`[a-zA-Z]`·`split('')`·`charCodeAt` 를 전부 훑었고, 남은 것은
`find-replace` 의 폴백 하나뿐입니다 — `u` 플래그가 거부될 때만 닿습니다.
`toLowerCase()` 는 전부 `tagName`(ASCII 보장), 정렬은 전부 숫자 비교입니다.

## 3. 계측을 잘못하면 "문제 없음" 이 나옵니다

이 세션에서 제일 비싸게 배운 것입니다. 아래는 전부 **실제로 잘못 재고 잘못된
결론을 문서에 적었다가 나중에 정정한** 것들입니다.

### 3-1. 커밋 횟수는 사용자가 보는 것을 재지 못합니다

#24 에서 undo 표시 지연을 **커밋 횟수** 로 쟀습니다. 서식 계산을 동기로
앞당겨도 2커밋/1어긋남이 그대로여서 "이벤트 순서 문제가 아니다" 라고
결론냈습니다.

**틀렸습니다.** preact 는 컴포넌트마다 `commitRoot` 를 부르므로 커밋 2회가
곧 프레임 2개가 아닙니다. 재야 할 것은 **커밋 사이에 페인트가 끼는지**
였고, 프레임 경계를 타임라인에 함께 놓자마자 원인이 드러났습니다 (#26).

### 3-2. 테스트가 통과해도 판별력이 없을 수 있습니다

#26 의 회귀 테스트를 `requestAnimationFrame` 으로 썼는데, **고치기 전에도
통과했습니다.** 코어가 클릭 중에 등록한 rAF 가 테스트 것보다 먼저 돌아 이미
교정된 뒤를 보기 때문입니다. 컨트롤(수정 되돌리기)을 돌려서 잡았습니다.

**교훈: 새 테스트는 고치기 전에 실패하는 것을 확인해야 합니다.** 이 세션의
수정마다 컨트롤(수정을 되돌리고 다시 돌리기)을 붙였고, 그 덕에 판별력 없는
테스트를 두 번 잡았습니다.

### 3-3. 판정 기준이 틀리면 거짓 실패가 납니다

같은 #26 에서 "문서에 `<strong>` 이 있는가" 로 판정했다가 redo 에서 실패했습니다.
캐럿이 굵은 글자 밖이면 툴바가 꺼져 있는 것이 **맞습니다.** 기준을
"코어가 말하는 상태"(`queryState`)로 바꿔야 했습니다.

### 3-4. 우회로 만든 측정은 무효입니다

자동 완성 원자성을 재려고 `AUTOCOMPLETE_SHOW` 를 직접 발행했더니 커밋이 0회
나왔습니다. `hideAutocomplete()` 가 플러그인 내부 플래그를 보는데 그 플래그를
우회했기 때문입니다. **플러그인의 실제 경로로 몰아야 했습니다.**

### 3-5. 앱이 쓰지 않는 경로를 재고 있었습니다

성능 검토 때 `document.queryCommandState` 를 재고 "코어가 비용의 99%" 라고
적었는데, 스파이를 붙여 보니 **레거시 호출이 0건** 이었습니다. 레지스트리
자체 구현은 0.0006 ms 로 200배 빨랐습니다.

### 3-6. 예측이 틀린 경우

`useSyncExternalStore` 가 훅과 같은 부류라 렌더 범위가 넓을 것으로 예상했는데
재보니 **신호와 같았습니다.** `getSnapshot` 을 필드 하나로 좁히면 컴포넌트마다
스냅샷 비교로 빠져나가기 때문입니다.

신호 도입 자체도 처음에는 "닫힌 다이얼로그의 지연 평가" 라는 **재보지 않은
근거** 로 권했다가 철회했고(실제 0.01 ms), 나중에 렌더 정밀도라는 다른 근거로
다시 채택했습니다. 그 과정에서 렌더 축의 이점을 잘못된 계측(시간)으로
기각했다가 두 번 지적받고 정정했습니다.

### 3-7. 이득이 0이면 되돌립니다

#24 에서 서식 계산을 동기로 앞당기는 변경을 두 번 시도했고, 숫자가 전혀 바뀌지
않아 **둘 다 되돌렸습니다.** 그때는 계측이 틀렸던 것이지만(3-1), _측정된 이득이
없으면 변경을 남기지 않는다_ 는 판단 자체는 유지합니다.

## 4. 이 세션이 남긴 규율

1. **트리거가 적혀 있어도 재보기 전에는 믿지 않습니다.** 우선순위 표의 다섯
   항목 중 넷을 쟀고 셋이 "아직 아님" 으로 닫혔습니다.
2. **새 테스트는 고치기 전에 실패시켜 봅니다.** 통과하는 테스트가 아무것도
   지키지 않을 수 있습니다.
3. **계측 도구를 먼저 의심합니다.** 커밋 횟수·시간·개수 중 무엇이 사용자가
   겪는 것에 대응하는지 확인하고 고릅니다.
4. **틀린 결론은 조용히 고치지 않고 정정 기록을 남깁니다.**
   `selection-state.md` §10, `phase-8-entry.md` §4 가 그렇게 쓰였습니다.
