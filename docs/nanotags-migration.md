# nanotags 이주 계획

> 상태: 제안(Draft) · 대상: `packages/ui`
> 관련: [`app-or-library.md`](./app-or-library.md), [`toolbar-options.md`](./toolbar-options.md)

## 요약 (결론 먼저)

1. **1번은 끝났고, 규칙 셋을 얻었습니다.** 폰트 메뉴가 커스텀 엘리먼트로 돌고
   테스트 10개가 통과합니다. 문서에 없는 제약 셋을 실측으로 찾았습니다(§2).
2. **급소는 nanotags 가 아니라 `kinu` 입니다.** 컴포넌트 28개 중 **11개**가
   kinu 를 쓰고, kinu 는 `peerDependencies: preact` 입니다. **kinu 를 안 걷어내면
   Preact 는 안 없어집니다** — 즉 이주가 끝나지 않습니다.
3. **이득이 마지막에만 옵니다.** 컴포넌트를 하나 옮길 때마다 비용은 즉시
   드는데, 번들 이득(~5 kB gzip)은 **마지막 하나까지 옮겨야** 나옵니다. 중간에
   멈추면 두 렌더러를 다 지고 갑니다. 이게 이 이주의 가장 위험한 성질입니다.
4. 그래서 계획을 **kinu 판단 앞뒤로** 자릅니다. 1단계는 kinu 없는 17개로
   패턴을 굳히고, **2단계에서 kinu 대체 비용을 재서 계속할지 정합니다.**
   거기가 되돌아갈 수 있는 마지막 지점입니다.
5. 유리한 조건 하나 — 테스트 21개 파일 중 **4개만** 렌더러를 압니다. 나머지는
   DOM 을 봅니다(질의 142곳). 렌더러를 갈아도 판별력이 삽니다.

## 2. 실측으로 얻은 규칙 셋 (문서에 없습니다)

**① 엘리먼트가 자기 마크업을 직접 만들어야 합니다.**
`withRefs` 는 `connectedCallback` 시점에 자식을 찾는데, Preact 는 엘리먼트를
붙인 **뒤에** 자식을 채웁니다 → `Missing elements for refs`. 나중에 refs 를 다시
푸는 방법이 문서에 **없습니다.** nanotags 의 예제는 전부 서버가 그려 둔 마크업을
전제합니다.

**② `<template>` 은 `renderList` 컨테이너 바깥.**
"컨테이너의 자식 중 이번 사이클에 속하지 않은 것은 전부 지운다"가 규약이라
안에 두면 첫 렌더에서 사라집니다.

**③ 묶음 있는 `<select>` 에는 `renderList` 가 반쪽입니다.**
컨테이너 하나를 통째로 소유하므로 `<optgroup>` 두 개는 컨테이너 두 개고, 묶음
꼴이 오가는 전환은 손으로 DOM 을 다시 세워야 합니다.

> 그래서 폰트 메뉴에서 nanotags 가 준 것은 **렌더링이 아니라 커스텀 엘리먼트
> 껍데기와 nanostores 배선**이었습니다. 이 비율이 다른 컴포넌트에서도 비슷하면,
> "렌더러 교체"가 아니라 "직접 DOM 조작 + 얇은 껍데기"로 가는 이주입니다.

### 덤으로 확인된 것

`subscribeToSelection`(IME 조합 중 무시 · 다음 프레임까지 지연 · 에디터 밖이면
건너뜀)은 **원래부터 Preact 를 안 쓰고 있었습니다.** 그대로 재사용했습니다.
이런 자리가 더 있는지 찾는 것이 이주 비용을 크게 줄입니다.

## 4. 급소 — `kinu`

`kinu@0.1.4` 는 `peerDependencies: { preact }` 입니다. 감싸든 미루든 **남아 있는
한 Preact 가 번들에 실립니다.**

쓰는 부품과 퍼짐:

| 부품 | 쓰는 컴포넌트 수 |
| --- | --- |
| **Dialog** | **6** |
| **Button** | **6** |
| Input | 4 |
| Label | 3 |
| DropdownMenu (+Trigger/Content/Item) | 2 |
| Toggle · ToggleGroup | 2 · 2 |
| MenubarItem | 2 |
| Menubar · Select · Tab · TabList · Checkbox | 각 1 |

**Dialog 6곳이 핵심입니다** — `document-dialog`, `find-replace-dialog`,
`image-dialog`, `link-dialog`, `special-character-dialog`, `table-dialog`.
이 여섯은 다이얼로그 대체 없이는 못 옮깁니다.

### 선택지

| | 내용 | 값 |
| --- | --- | --- |
| **A. 직접 만든다** | 필요한 부품 12종을 nanotags 로 | 통제권 최대. 접근성·포커스 트랩·`<dialog>` 동작을 다시 책임집니다 |
| **B. 하이브리드로 산다** | kinu 컴포넌트는 Preact 로 남김 | 이주가 **끝나지 않습니다.** 두 렌더러를 영구히 지고 갑니다 |
| **C. 다른 라이브러리** | 웹 컴포넌트 UI 라이브러리로 교체 | kinu 도입 판단(`kinu-evaluation.md`)을 다시 여는 일 |

지금 기울기는 **A**, 단 §5 의 관문을 통과할 때만입니다. B 는 "이주"가 아니라
"영구 하이브리드"이므로 그렇게 부르고 결정해야 합니다.

## 5. 골짜기 — 이득이 마지막에만 옵니다

이게 이 계획에서 가장 중요한 부분입니다.

| | gzip |
| --- | --- |
| preact | 4.80 kB |
| @preact/signals(+core) | 3.75 kB |
| **합계** | **8.55 kB** (앱 JS 63.9 kB 의 **13.4%**) |
| nanotags + nanostores | ~3.5 kB |
| **순 이득** | **약 5 kB (JS 의 8%)** |

**이 5 kB 는 마지막 컴포넌트를 옮긴 뒤에야 나옵니다.** 하나라도 Preact 를 쓰면
런타임이 통째로 실립니다. 즉 —

- 비용은 **컴포넌트마다** 발생
- 이득은 **전부 끝나야** 발생
- 중간에 멈추면 **두 렌더러 + 두 상태 라이브러리**를 지고 갑니다

그래서 "조금씩 해 보고 아니면 만다"가 성립하지 않는 이주입니다. 되돌릴 수 있는
지점은 **kinu 에 손대기 전**뿐입니다.

> 다만 번들 크기가 이 이주의 유일한 이유는 아닙니다. 웹 컴포넌트의 고유 이득은
> **남의 페이지에 심는 것**인데, 그건 [`app-or-library.md`](./app-or-library.md)
> 가 닫아 둔 라이브러리 경로입니다. 그 문을 다시 열 생각이면 5 kB 는 부차적인
> 근거가 되고, 열 생각이 없으면 **5 kB 가 이 이주가 사는 유일한 값**입니다.
> 2단계 관문에서 이걸 먼저 정해야 합니다.

## 6. 단계

### 0단계 — 계기판 (완료)

테스트가 페이지 크래시로 조용히 빠지던 문제를 잡았습니다. core 1110/1110,
ui 135/135, `pnpm test` 가 두 패키지를 다 돕니다. **이게 없으면 이주 중에 내가
깬 것과 원래 깨져 있던 것을 구분할 수 없습니다.**

### 1단계 — kinu 없는 17개

작은 것·테스트가 지키는 것부터. 순서 제안:

1. `horizontal-rule-button`(20) · `indent-buttons`(28) — 버튼 하나짜리, 패턴 확인
2. `font-size-select`(31) · `line-height-select`(31) · `letter-spacing-select`(31) ·
   `heading-select`(40) — 폰트 메뉴와 같은 꼴이라 거의 복사
3. `alignment-buttons`(64) · `history-buttons`(62) — 상태 구독 있음
4. `color-picker`(204) · `more-menu`(200) · `auto-save-indicator`(293) — 큰 것
5. `editing-area`(44) · `editor-container`(24) · `toolbar`(148) — 껍데기

**관문**: 매 컴포넌트마다 ui 테스트 135개가 그대로여야 합니다. 줄면 멈춥니다.

**여기서 답이 나와야 하는 것**: 규칙 셋이 17개에 다 통하는가, 아니면 컴포넌트
종류마다 새 규칙이 나오는가. 후자면 비용 추정이 크게 틀린 것입니다.

### 2단계 — 관문: kinu 를 어떻게 할 것인가 ★

**여기가 되돌아갈 수 있는 마지막 지점입니다.**

정할 것:

- [ ] 라이브러리 경로를 다시 열 것인가 (§5 각주) — 이게 이주의 값을 정합니다
- [ ] A(직접) / B(하이브리드) / C(다른 라이브러리) 중 무엇인가
- [ ] A 라면 **Dialog 하나를 먼저 만들어 재 봅니다** — 접근성·포커스 트랩·
      Esc·백드롭까지. 그 비용 × 12종이 전체 추정이 됩니다

**중단 조건**: Dialog 하나가 예상보다 크게 비싸면 B 로 선언하고 **그렇게
부릅니다**. "이주 중"이라고 부르면서 영구 하이브리드로 사는 게 제일 나쁩니다.

### 3단계 — kinu 의존 11개

2단계 결정에 달렸습니다. Dialog 6곳이 가장 큰 덩어리.

### 4단계 — Preact 걷어내기

- `lucide-preact` 15파일 → 인라인 SVG
- `EditorProvider`(Preact 컨텍스트) → `sagak-editor-provider` 만 남김
- `elements/editor-context.ts` 의 JSX 선언 삭제
- `preact` · `@preact/signals` · `kinu` 제거

**여기서만 5 kB 가 나옵니다.**

## 8. 열린 질문

1. **`ui ↔ app` 경계를 먼저 접을 것인가?**
   `toolbar-options.md` §2.4 에서 "85줄짜리 셸이 정당화 못 하는 경계"로 결론냈고
   아직 안 했습니다. 이주와 독립이지만, 먼저 접으면 이주 대상이 한 자리로
   또렷해집니다.

2. **nanotags 가 0.15.2 입니다.**
   1.0 이전이고 테스트 이야기가 문서에 없습니다. 규칙 셋이 전부 문서 밖에서
   나왔다는 것도 같은 신호입니다. 파손적 변경이 오면 그때 무엇을 할지 —
   지금은 답이 없고, 이것도 2단계 관문에서 값에 넣어야 합니다.

3. **`renderList` 를 계속 쓸 것인가?**
   폰트 메뉴에서는 반쪽이었습니다. 1단계에서 목록을 그리는 컴포넌트를 몇 개 더
   지나 보면 답이 나옵니다. 안 쓰기로 하면 nanotags 는 **커스텀 엘리먼트 껍데기
   + nanostores 배선**만 남고, 그러면 "nanotags 를 쓸 이유"가 더 얇아집니다.
